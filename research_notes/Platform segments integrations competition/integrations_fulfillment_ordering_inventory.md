# Fulfillment, shipping, food ordering/delivery and inventory integrations for the app menu

Scope: the shipping, delivery, online-ordering and inventory connectors a Cloudflare-Workers small-business site engine should offer in its owner dashboard "app menu", with for each one: OAuth yes/no, partner gating and typical approval time, webhooks, cost, and what the site would do with it. Research date: 5 October 2026, US market. Serves the founder vision (one engine, food / retail / presence / custom variants, OAuth-first connectors with API-key + webhook fallback, solo founder, family auto parts store as the flagship "custom" customer).

Method note: the sandbox egress proxy blocked every first-party vendor docs host attempted (docs.shipstation.com, shipengine.com, docs.goshippo.com, developer.doordash.com, developer.uber.com, doc.toasttab.com, autocare.org, support.pirateship.com, g2.com, supergood.ai, hookdeck.com). Findings therefore rest on (a) WebSearch result extracts that quote vendor pages, (b) the open-source Nango providers catalog fetched from raw.githubusercontent.com (an authoritative, machine-readable record of each API's auth mode), and (c) secondary pages for pricing. Anything not confirmed from a vendor page is marked **(unverified)** with the last figure and date seen.

## Key question 1: What should the shipping / fulfillment shelf of the app menu contain, and how does each connector authenticate?

### Takeaway
No mainstream shipping API that a merchant brings to the site supports a merchant-facing OAuth "Connect" button except Shippo (platform OAuth that even creates the merchant's Shippo account inside the flow) and the carriers themselves (UPS Authorization Code, USPS/FedEx OAuth 2.0 client credentials). ShipStation and EasyPost are API-key products, so the app menu needs a first-class "paste your key" path with webhook registration done by the engine; Pirate Ship has no API at all and should be a CSV export/import feature, not a connector.

### Inferences
- For the CatholicJoe-derived engine, the cheapest path is to keep the existing ShipStation V1 connector (key+secret) and add V2 (single key + RSA-signed webhooks) as a second "ShipStation" option; both are owner-pasted keys. The ShipStation Partner API is for provisioning accounts under a reseller agreement and is not needed to let an owner connect an existing account.
- Shippo is the only shipping connector that satisfies the founder's "owner never sees an API key" rule and also handles merchants who have no shipping account yet (account created in the OAuth flow). It should be the default "Ship with Shippo" tile; ShipStation/EasyPost become "I already use X" tiles.
- Carrier-direct OAuth (UPS Authorization Code, USPS v3, FedEx) adds negotiated-rate accuracy but triples the surface area (three label formats, three tracking models). For a solo founder, carriers should be reached through Shippo/ShipStation rather than integrated directly until a customer demands it.
- Pirate Ship is popular with very small shops; a "Download Pirate Ship CSV" button and "Upload tracking CSV" importer costs an afternoon and covers them without an API.

### Gaps
- Could not open ShipStation's own V2 webhook event list or confirm V2 webhook retry/signing details beyond the Hookdeck summary (docs host blocked).
- Shippo webhook event list, platform fee (if any) and whether Shippo imposes a platform review before issuing OAuth credentials: not confirmed (docs blocked).
- EasyPost 2026 pricing is from a reseller blog, not easypost.com.
- Stamps.com REST API status in 2026 and whether new integrator registrations are still accepted post-Auctane consolidation: not found.

## Key question 2: What should the food ordering / delivery shelf contain, and what is realistically available to a small platform?

### Takeaway
Every first-party delivery marketplace API (DoorDash Marketplace, Uber Eats, Grubhub) is partner-gated with demos, NDAs, certification and no published timeline; DoorDash Drive (white-label delivery from the restaurant's own site) is the only delivery API with a self-serve developer portal, but its production access is "currently restricted" with "no timeline". The practical food shelf for a solo founder is: (1) the site's own ordering with Square OAuth as the order/POS backbone, (2) DoorDash Drive for white-label delivery when access is granted, (3) an aggregator (Checkmate ~$115/location/month, Cuboh ~$119/month, Deliverect/Chowly custom) that already holds the marketplace credentials and exposes a partner API, and (4) Toast/Clover order sync for restaurants already on those POS systems.

### Inferences
- The founder's "integrates with DoorDash" promise is achievable in three different senses with very different effort: (a) a Storefront/Marketplace "Order on DoorDash" button (zero API work, available to every restaurant on day one); (b) DoorDash Drive white-label delivery from the site's own checkout (self-serve dev portal, but production gated by a demo and an explicit "restricted, no timeline" notice in 2026); (c) Marketplace menu/order sync (partner certification, SSIO for multi-merchant middleware; realistically months and a BD relationship). Ship (a) immediately, build (b) against the sandbox and submit once one real restaurant is live, treat (c) as "via aggregator" only.
- An aggregator partnership (Checkmate, Otter, Deliverect, Chowly) is the realistic way to show marketplace orders inside the owner's dashboard without holding DoorDash/Uber/Grubhub partner credentials; the merchant pays ~$115–$230/month and the engine integrates once with the aggregator's partner API instead of three gated marketplaces. The aggregators themselves are sales-led for partner API access, so even this needs one BD conversation.
- Square is the single best first POS/online-ordering connector: self-serve OAuth, menu (Catalog), orders, inventory and webhooks in one account, no partner review required to call the APIs. Clover is the second (OAuth, app required). Toast is partner-gated and should wait until a Toast restaurant is a paying customer.
- The site should own the order and the payment (Stripe Checkout already exists in the engine) and treat delivery as a fulfillment step; this keeps the restaurant off marketplace commissions on orders the site generates, which is the strongest sales pitch versus Storefront.

### Gaps
- DoorDash Drive current (2026) per-delivery pricing and whether a multi-merchant "developer serving other businesses" account is permitted were not confirmable (developer portal blocked); Drive integration requirements for platforms vs single merchants are unknown.
- Uber Eats and Grubhub typical approval times: no public figures; both are described only as partner-manager/pilot driven.
- Whether Checkmate, Chowly and Cuboh offer a partner-facing API for a website platform (as opposed to POS vendors) was not found; Cuboh's current status (2026) is unverified.
- Toast partner program fees, revenue share and typical approval duration not found.

## Key question 3: Which inventory systems should the custom tier integrate with, and how?

### Takeaway
The retail POS/inventory systems a small shop is likely to run (Square for Retail, Lightspeed X-Series, Shopify, Clover) all expose OAuth 2.0 and self-serve developer apps, so an OAuth-first "sync stock from my POS" tile is feasible without partnerships; the dedicated inventory tools (Cin7 Core, inFlow, Zoho Inventory, Odoo) are mostly API-key or OAuth-via-add-on and lack reliable webhooks, so they need polling sync.

### Cited Findings

| System | Auth | Webhooks | Price (merchant) | Notes for the engine |
|---|---|---|---|---|
| Square (incl. Square for Retail) | OAuth 2.0 | Yes (orders, inventory, catalog) | Square plan + processing | Catalog + Inventory API give SKU, variations, quantity by location |
| Lightspeed Retail X-Series (ex-Vend) | OAuth 2.0 for marketplace add-ons; personal tokens for single-retailer | Yes **(unverified)** | Lightspeed subscription | Products, inventory levels, outlets, sales |
| Shopify | OAuth 2.0 (public/custom app) or client-credentials; Admin API | Yes | Shopify plan | Only relevant when a merchant insists on keeping Shopify as system of record |
| Clover | OAuth 2.0 via app | Yes | Clover plan | Inventory + orders |
| Zoho Inventory | OAuth 2.0 (Zoho accounts) | Yes **(unverified)** | Zoho plans | Items, stock, sales orders |
| Odoo | XML-RPC/JSON-RPC with API key by default; OAuth 2.0 only through the third-party Synconics REST module | No native | Community free / Enterprise per user | Self-hosted; treat as "custom integration" |
| Cin7 Core (ex-DEAR) | API key (account ID + key) | Yes **(unverified)** | from ~$349/mo | Mid-market; rare at this customer size |
| inFlow | API (bearer) | "does not publish a native webhook contract" | from ~$186/mo | Poll products/stock/orders |
| Sortly | No API details found | — | — | Gap |

### Inferences
- For the "$40k–$100k custom inventory" tier the engine should not try to replace the POS; it should own the web catalog and pull quantity-on-hand from the POS via OAuth (Square, Lightspeed, Clover, Shopify) on webhooks plus a periodic reconciliation poll. That is one adapter interface (`getStock(sku, location)`, `onStockChanged`) with four implementations.
- Odoo/inFlow/Cin7/Zoho connectors belong behind an "API key + polling" fallback tile, built only when a paying customer runs that system.
- Sortly's API status is unknown; do not promise it.

### Gaps
- Sortly API existence, auth and pricing: no reliable source found in the search budget.
- Lightspeed partner-program requirements for listing an add-on (review, fees) not found.
- Zoho Inventory and Cin7 Core webhook availability was not confirmed from vendor pages.

## Key question 4: What does the auto parts store (full inventory online) need, and which auto-parts data/ordering systems matter?

### Takeaway
An auto parts site with real inventory needs three things the generic retail variant does not have: licensed fitment data (ACES/PIES from the Auto Care Association, from $2,500/yr entry level for a sub-$1M member, or catalog coverage via Epicor PartExpert / WHI Nexpart), a sync to the store's point-of-sale (commonly Epicor Eagle/Vision, whose APIs are fragmented, on-prem and in practice brokered by Modern Retail), and commerce rules for core charges and local pickup. PartsTech, Nexpart and MyPlace4Parts are B2B shop-facing ordering networks (partner-gated, no public sandbox), relevant to the store as a seller rather than to the consumer site.

### Cited Findings
- ACES/PIES Entry Level Package "for member companies under $1 Million in global revenue costs $2,500 and includes all databases required to create and/or receive ACES and PIES XML files, including VCdb, Qdb, PCdb, PAdb, and Brand Table"; North America Light Duty & Powersports VCdb Level 1 (under $1M) members $3,150 / non-members $4,410; Level 2 ($1–2M) $3,675 / $5,145; VCdb subscription includes Qdb, PCdb and Brand Table; PAdb $1,100–$5,500 members, $2,300–$15,950 non-members by revenue — [Auto Care Association subscriptions](https://www.autocare.org/data-and-information/data-standards/subscriptions) (figures via search extract; page blocked for direct fetch) **(unverified current year)**
- ACES = Aftermarket Catalog Exchange Standard (part-to-vehicle applications); PIES = Product Information Exchange Standard (product attributes, pricing, images, packaging) — [Hedges & Company ACES/PIES Q&A](https://hedgescompany.com/?p=42988); [PCFitment beginner guide](https://blog.pcfitment.com/automotive-data-standards-aces-pies-beginners-guide/)
- Epicor PartExpert / Catalog API: "more than 17 million part numbers/SKUs from over 9,500 manufacturer product lines, covering in excess of 1.4 billion vehicle applications"; "With the Epicor Catalog API, you can create custom applications that deliver accurate and searchable parts listings" — [Epicor Part Expert](https://www.epicor.com/en/products/supply-chain-management-scm/part-expert/); [Epicor catalog for automotive](https://www.epicor.com/en/products/digital-commerce/catalog-for-automotive/)
- Epicor Eagle (retail ERP/POS for parts stores): "Eagle's API/documentation is fragmented and not co-located with Epicor's main developer docs, and Eagle ecommerce integrations are effectively outsourced to Modern Retail's tiered packages ... on-prem Eagle deployments mean integrations must handle store-by-store networking, VPN access, and intermittent connectivity" — [Supergood Epicor Eagle API report](https://supergood.ai/api-report-card/epicor-eagle); third-party Eagle connectors exist for X-Cart, Wayfair, Walmart — [Clarity Ventures Epicor Eagle x X-Cart](https://www.clarity-ventures.com/integrations/epicor-eagle-x-cart)
- WHI Nexpart: NEXLINK spec "enables end users to punch out to Nexpart directly from a third-party application ... include part information or vehicle information such as VIN, and in return, part numbers, part descriptions, pricing, and other order details are sent back"; Nexpart integrates sellers' inventory, shipping, customer pricing levels, card processing and eBay via eBay Link; shop-management systems can query/ordering through WHI Nexpart, PartsTech, Parts Authority, WorldPac SpeedDIAL and MyPlaceForParts — [WHI Solutions integration tools](https://www.whisolutions.com/products/integration-tools/); [Identifix Shop Manager: Using WHI Nexpart](https://support.shopmanager.identifix.com/support/solutions/articles/43000686748-using-whi-nexpart)
- PartsTech "offers a partner-facing REST API — the PartsTech External API — used by 35+ shop management systems ... covering catalog search, VIN lookup and partner callbacks. However, getting production credentials runs through a partner integration process, with no sandbox and no listed SDKs" — [Supergood PartsTech report](https://supergood.ai/api-report-card/partstech); API terms at [PartsTech API agreement](https://partstech.com/api-agreement-terms/)
- MyPlace4Parts "is an eCommerce product of the Aftermarket Auto Parts Alliance Inc. ... access to more than 1.9 million catalog items" (B2B ordering portal for Alliance/Auto Value/Bumper to Bumper members) — [Vehicle Service Pros: Shop-Ware integrates with MyPlace4Parts](https://www.vehicleservicepros.com/aftermarket-business-world/news/press-release/21242298/shop-ware-inc-shop-ware-integrates-with-myplace4parts)
- Required storefront features per automotive e-commerce vendors: "Year-make-model search is the first filter for most parts stores"; "intelligent core charge management that automatically calculate and display core charges ... base price plus any core deposit, which you receive back when you return the old component"; fitment data shown on product page; "Shopify, WooCommerce, and Ecwid usually need a fitment app or custom data layer"; "Real-time warehouse distributor sync ... automated inventory and pricing updates to help prevent oversells" — [Web Shop Manager automotive](https://webshopmanager.com/automotive-ecommerce/); [Convermax YMM fitment search](https://convermax.com/year-make-model-fitment-search); [OuterBox auto parts web design](https://www.outerboxdesign.com/?p=1957)

### Inferences
- Minimum viable auto-parts site for the family store: (1) product catalog imported from the store's POS export (Eagle/other) with SKU, brand, qty-on-hand per location, price and core-charge amount; (2) a vehicle selector (year → make → model → engine/submodel) backed by VCdb IDs; (3) an applications table mapping SKU to BaseVehicle/Engine/qualifiers; (4) checkout rules: core charge as a separate refundable line, "pickup in store" as the default fulfillment with Stripe Checkout, shipping via Shippo/ShipStation for shippable parts, "call for availability" when qty is 0; (5) nightly or webhook-driven stock sync from the POS.
- Fitment data strategy: license the Auto Care VCdb (about $3k–$4k/yr) or the $2,500 entry package in the store's name, then load the supplier-provided ACES/PIES files the store already receives from its warehouse distributor; Epicor Catalog API is the enterprise alternative (price not published). Do not attempt to scrape or infer fitment.
- Nexpart/PartsTech/MyPlace4Parts are channels where the store sells to repair shops; they matter for the store's wholesale side and could be a later "list my inventory on Nexpart" integration, but they are partner-gated and the engine should not depend on them.
- Eagle integration is the biggest unknown and should be scoped as a custom project (VPN/on-prem file export) rather than an app-menu tile.

### Gaps
- Which POS the family store actually runs (Eagle, Vision, a jobber system, or something else) is unknown; the integration approach depends entirely on it.
- Epicor Catalog API licensing cost and whether a single retailer can license it: not found.
- Whether warehouse distributors supply ACES/PIES files to independent retailers at no charge: not confirmed.
- Current (2026) Auto Care subscription prices could not be read from autocare.org directly.

## Key question 6: Data model implications of fitment-style attributes

### Takeaway
Fitment is a many-to-many relation between a part and a vehicle configuration with qualifiers, not a product attribute; the engine's product table needs a generic attribute layer (PIES-style) plus a separate applications table keyed to licensed VCdb identifiers, and the vehicle selector must query the applications table, not the product search index.

### Cited Findings
- ACES describes part-to-vehicle applications and PIES describes product attributes; VCdb (Vehicle Configuration database) supplies vehicle IDs, Qdb supplies qualifiers, PCdb supplies part types/positions, PAdb supplies product attributes; a VCdb subscription "automatically provides access to the Qualifier database (Qdb), Product Classification database (PCdb) and Brand Table" — [Auto Care subscriptions](https://www.autocare.org/data-and-information/data-standards/subscriptions); [Credencys ACES/PIES deep dive](https://www.credencys.com/blog/managing-product-data-auto-parts-aces-pies); [Anglera ACES glossary](https://www.anglera.com/glossary/aces-aftermarket-catalog-exchange-standard)
- Generic platforms "need a fitment app or custom data layer" because fitment does not fit a flat product schema; YMM search "filters out products by vehicle and shows customers only parts that fit" — [Convermax](https://convermax.com/year-make-model-fitment-search); [Web Shop Manager](https://webshopmanager.com/automotive-ecommerce/)
- Core charges are a separate refundable deposit line on top of base price — [Web Shop Manager](https://webshopmanager.com/automotive-ecommerce/)

### Inferences
- Schema sketch for the D1-backed engine: `product` (sku, brand_id, part_type_id from PCdb, price, core_charge, qty_by_location JSON or `stock` table, shippable flag, hazmat flag); `product_attribute` (product_id, padb_attribute_id, value, uom) for PIES attributes; `vehicle` (vcdb base_vehicle_id, year, make, model, submodel, engine) loaded from VCdb; `application` (product_id, base_vehicle_id, engine_id?, submodel_id?, position_id?, qualifier_ids JSON, qty, note). The YMM selector resolves to base_vehicle_id then joins `application` → `product`. Full-text search stays on `product`.
- The same attribute layer serves the clothing variant (size/color) and food variant (modifiers), so "fitment" is the stress test that justifies a generic attribute table in the engine rather than a one-off auto parts schema.
- VCdb row counts are large; keep VCdb in D1 only for the makes/models/years the store actually stocks parts for, or in a KV/R2-backed static index, and refresh on each quarterly Auto Care release. Exact VCdb size was not verified.
- Licensing: VCdb IDs embedded in the store's database are permitted for the subscriber; redistributing the database to other tenants of the engine is not, so each auto-parts tenant needs its own subscription (or the engine licenses it as a data provider at the higher non-member/reseller tier, which was not priced in this research).

### Gaps
- Auto Care redistribution/reseller terms for a multi-tenant platform: not found.
- VCdb size and release cadence: not verified in this session.
