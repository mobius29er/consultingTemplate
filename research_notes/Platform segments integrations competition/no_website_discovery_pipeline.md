## Q1. Foursquare OS Places: schema, hosting, size, filters, freshness, share of US rows with no website

### Takeaway
FSQ OS Places remains the best-documented single-vendor open POI file (Apache 2.0 with a NOTICE-preservation duty; 22 columns including `tel`, `website`, `email`, `instagram`, `facebook_id`, `date_refreshed`, `date_closed`), but as of this session its S3 objects are not anonymously readable and the Hugging Face copy is reported gated, so treat direct FSQ bulk access as "requires a Foursquare/HF account" until re-checked. The same Foursquare rows are republished inside Overture under Apache 2.0 and were readable there, so the pipeline below uses Overture as the primary bulk source and FSQ as an optional second source.

### Cited Findings
- License and attribution duty (primary, fetched from the bucket): "The Foursquare OS Places dataset (the "Data") is licensed under the Apache License, Version 2.0 ... if you use, modify, or distribute the Data, you must: provide recipients with a copy of the License ... preserve attribution to Foursquare, including preserving the full content of this NOTICE.txt file ... if using/distributing the Data in API form ... include a copy of the content from this NOTICE.txt file prominently in your developer documentation"; NOTICE last modified 2025-10-03, LICENSE 2024-11-14 — [s3 NOTICE.txt](https://fsq-os-places-us-east-1.s3.amazonaws.com/NOTICE.txt); [s3 LICENSE.txt](https://fsq-os-places-us-east-1.s3.amazonaws.com/LICENSE.txt)
- Columns (22): fsq_place_id, name, latitude, longitude, address, locality, region, postcode, admin_region, post_town, po_box, country, date_created, date_refreshed, date_closed, tel, website, email, facebook_id, instagram, twitter, fsq_category_ids, fsq_category_labels, placemaker_url, geom, bbox (as listed in the existing note from the FSQ schema page and the ClickHouse sample) — [FSQ Places OS schema](https://docs.foursquare.com/data-products/docs/places-os-data-schema) (blocked this session; secondary via search)
- Field semantics (secondary, search summary of the schema page): `date_closed` = "The date the POI was marked as closed in our database. This does not necessarily mean the POI actually closed on this date."; `date_refreshed` = "The date the POI last had any single reference refreshed from crawl, users or human validation."; `facebook_id` = "This POI's Facebook ID, if available." — [FSQ Places OS schema](https://docs.foursquare.com/data-products/docs/places-os-data-schema)
- Hosting and layout (secondary): Parquet on S3 at `s3://fsq-os-places-us-east-1/release/dt=YYYY-MM-DD/places/parquet/` (first release dt=2024-11-19 as 25 files `places-00000..00024.snappy.parquet` of ~455 MB each); from December 2024 (dt=2024-12-03) the release switched to GeoParquet with Zstandard compression, "geospatially partitioned following Open GeoParquet standards, using Fused" — [search summary of Foursquare blog / source.coop / Simon Willison](https://feeds.simonwillison.net/2024/Nov/20/foursquare-open-source-places); [FSQ release notes](https://docs.foursquare.com/data-products/docs/places-release-notes)
- Latest release and gating (secondary, search summary, October 2026): "the latest release is dt=2026-09-15 for both places and categories in parquet format, and the dataset is now gated on Hugging Face"; the August 2026 release "includes 390K+ new places with 13.8M+ places updated" and is also distributed on Databricks, Snowflake and the Places Portal — [Hugging Face dataset README](https://huggingface.co/datasets/foursquare/fsq-os-places/blob/main/README.md); [Foursquare on X, August 2026 release notes](https://x.com/Foursquare/status/2087295161193902399)
- Total size (secondary): the Hugging Face mirror is listed at 10.51 GB, 100M+ POIs, 200+ countries, 22 attributes, monthly updates — [hyper.ai dataset listing](https://hyper.ai/en/datasets/36514)
- Anonymous S3 access check (measured, 2026-10-05): `ListObjectsV2` on the bucket root returns only `LICENSE.txt` and `NOTICE.txt`; listing `release/` returns zero keys; HEAD on `release/dt=2026-09-15/places/parquet/places-00000.snappy.parquet` (and `.zstd.parquet`, `.parquet`, `part-00000.zstd.parquet`) and on 23 other candidate monthly dates all returned HTTP 404 — [bucket listing](https://fsq-os-places-us-east-1.s3.amazonaws.com/?list-type=2&delimiter=/)
- Foursquare-sourced rows inside Overture carry `sources[].dataset = 'Foursquare'` and `sources[].license = 'Apache-2.0'`; in a 1-in-16 row-group sample of the Overture 2026-09-23.1 places release, 69,020 of 1,131,545 US rows (6.1 %) had Foursquare as a base source (measured) — [Overture places release 2026-09-23.1 on S3](https://overturemaps-us-west-2.s3.amazonaws.com/?list-type=2&prefix=release/2026-09-23.1/theme=places/type=place/)
- Overture's own April 2026 tally: Foursquare-sourced = 6,749,057 features, Meta-sourced = 59,413,511 (from the existing note) — [Overture Places Guide](https://docs.overturemaps.org/guides/places)

### Inferences
- Filter for the target segment in FSQ terms (unverified against a live file this session): `country = 'US' AND tel IS NOT NULL AND website IS NULL AND date_closed IS NULL`, optionally `AND date_refreshed >= current_date - INTERVAL 24 MONTH` to drop stale rows. Metro restriction: cheapest is `region = 'TN' AND locality IN (...)` or a postcode list; most robust is a bbox on `latitude`/`longitude` (or the `bbox` struct's xmin/xmax/ymin/ymax, which lets the Parquet reader skip row groups). Because the December-2024 switch to GeoParquet made files spatially partitioned, a bbox predicate on `bbox.xmin`/`bbox.ymin` touches only a few of the files.
- Share of US rows with no website: no FSQ-only figure could be measured because the objects were unreadable. The Overture US sample (which contains the FSQ rows plus Meta, Microsoft, BrightQuery and others) gives 20.7 % of US rows with no website at all and 13.8 % with a phone but no website (Q2). For FSQ alone the existing note's observation that "many fields are null for many places" suggests the no-website share is higher than Overture's (estimate: 30-50 %, unverified), because Overture conflates several providers and takes the union of their websites.
- Quality caveats specific to FSQ: `date_closed` is when Foursquare learned of the closure, not the closure date, and the field is null for places that closed without a signal; `date_refreshed` is the only staleness signal and refreshes on any single reference, so a 2023 refresh date does not prove the phone is current. Expect duplicate rows for the same storefront (chains, moved businesses) and keep the dedup rules from the existing note Q8.
- Practical access route: request access on Hugging Face (gated), or use the Foursquare Places Portal / Snowflake / Databricks listings; pulling a 10.5 GB file monthly is unnecessary because the filtered metro slice is a few thousand rows.

### Gaps
- The FSQ schema page, release notes and Hugging Face card were blocked; column descriptions beyond the three quoted are from the existing note. The exact current S3 object naming for dt=2026-09-15 and whether anonymous S3 access was intentionally removed (vs a path change) are unverified; re-run `aws s3 ls s3://fsq-os-places-us-east-1/release/ --no-sign-request` from a machine without the proxy.
- No published statistic for the share of FSQ US rows with `website IS NULL` was found; the Overture-derived numbers in Q2 are the substitute.

## Q2. Overture Maps places: schema, DuckDB over S3, licensing per source, whether confidence filters remove stale rows

### Takeaway
Overture places (release 2026-09-23.1: 16 zstd parquet files, 11.0 GB, 81,455,423 rows) is anonymously readable from `s3://overturemaps-us-west-2` and carries `websites`, `socials`, `emails`, `phones`, `addresses`, `confidence`, `operating_status` and a per-row `sources[].license`, so the "phone but no website" slice for one metro can be pulled in under ten seconds with a bbox predicate. Measured for the Jacksonville, FL bbox: 78,652 rows, 10,656 with phone and no website, 8,144 of those open with confidence >= 0.5; for a Chattanooga-sized bbox: 27,381 rows, 3,347 phone/no-website, 2,665 after the open+confidence filter. Every US row in the sample was CDLA-Permissive-2.0, Apache-2.0 (Foursquare) or CC0-1.0 (AllThePlaces); no ODbL rows appeared in the places theme.

### Inferences
- Do confidence filters remove stale rows? Partly. `operating_status` is the explicit closure flag but is null for 25 % of rows (6,905 of 27,381 in Chattanooga), so "not permanently_closed" alone keeps unknowns. Confidence is an existence score, re-derived from third-party signals since April 2026, so `confidence >= 0.5` removes the bottom ~9-10 % of rows (2,535 / 27,381; 7,829 / 78,652) which are disproportionately dormant listings, and `>= 0.75` removes a further ~13 %. Neither field says whether the phone still rings; that remains a verification step (Q7). Recommended default: `(operating_status IS NULL OR operating_status = 'open') AND confidence >= 0.5`, then rank by confidence descending and by `sources[].update_time` recency.
- Licensing per row is machine-readable: keep `sources[0].dataset` and `sources[0].license` on the CRM row. For a private CRM all three licenses seen (CDLA-Permissive-2.0, Apache-2.0, CC0-1.0) permit storage and commercial use; the Apache-2.0 rows carry the NOTICE duty from Q1 if you ever redistribute them. If an ODbL row ever appears (none did in the US sample), see Q3.
- Expected row counts for a mid-sized US metro (~0.5-0.7 M population, bbox roughly 50 x 40 km): ~25-30 k Overture places, ~3-3.5 k with phone and no website, ~2.5-2.7 k after open+confidence>=0.5, ~1.8 k at confidence>=0.75, of which roughly one third have no social URL at all (estimate, from the Chattanooga measurement). After removing categories that are not customers (places of worship, real-estate agents, government, historic sites, health systems) the actionable list is roughly 1,500-2,000 rows (estimate).

### Gaps
- The Overture Places Guide and 2026 release notes could not be fetched; license statements above are from the schema fields observed in the data plus secondary summaries. The CDLA-Permissive-2.0 text itself was not fetched (cdla.dev not attempted); its attribution/notice requirement should be confirmed before any redistribution.
- The sandbox could not download DuckDB's httpfs/spatial extensions (extensions.duckdb.org returned 403), so the DuckDB SQL in Q9 was validated by executing the same predicates with pyarrow against the same files rather than inside DuckDB.

## Q3. OpenStreetMap via Overpass or Geofabrik: contact tags and ODbL implications for a private CRM

### Takeaway
OSM is a thin third source for this use case (website/phone tags exist but coverage of small US businesses is sparse and uneven) and its ODbL share-alike only bites on Public Use, so an internal founder CRM that never publishes the merged table has no obligation beyond attribution when something OSM-derived is shown. Keep OSM-derived rows tagged so they can be excluded from anything you later publish (for example a public "businesses near you" directory on a client site).

### Cited Findings
- Overpass public-instance limits and the ODbL attribution/share-alike framing are in the existing note (Q2 there): one-off use fine under ~10,000 queries/day and < 1 GB/day; regular automated use should self-host — [Overpass API User's Manual](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html); [OSM wiki: Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API)
- Internal use (secondary, search summaries of the OSMF Licence and Legal FAQ and the OSM wiki use-cases page): "If you are only using OpenStreetMap data and any Derivative Database internally and do not make Public Use of the data, then you do not have to share anything with anybody."; "ODbL does not require you to publish derivative databases, but the public use of a derived database or work produced from a derived database requires that an offer of the derived database is made available."; "Derivative Databases can trigger share-alike with respect to non-OSM data if the Derivative Database is Publicly Used; and Collective Databases, where share-alike only applies to the parts containing or derived from OSM-data." — [OSMF Licence and Legal FAQ](https://osmfoundation.org/wiki/Licence_and_Legal_FAQ); [OSM wiki: License/Use Cases](https://wiki.openstreetmap.org/wiki/License/Use_Cases); [OSM-legal-talk, June 2022](https://lists.openstreetmap.org/pipermail/legal-talk/2022-June/009163.html)
- Tag vocabulary: both `website`/`contact:website`, `phone`/`contact:phone`, `email`/`contact:email`, `contact:facebook`, `contact:instagram` are in use; the `contact:*` scheme and the bare keys coexist — [OSM wiki Key:contact](https://wiki.openstreetmap.org/wiki/Key:contact) (blocked this session; the key list is from the existing note's OSM background and general knowledge, unverified here)
- Overture's places theme, which already aggregates several providers, showed no ODbL-licensed rows in the US sample (Q2, measured), so OSM data would have to be pulled separately to add anything.

### Inferences
- Overpass query shape for the segment: nodes/ways with `shop`, `amenity`, `craft`, `office` or `healthcare` tags inside a bbox, having `phone` or `contact:phone` and lacking `website` and `contact:website`; output `name`, `addr:*`, the phone tags and `contact:facebook`. Run it once per metro against a self-hosted or paid Overpass instance (per the existing note), or use osmium on a Geofabrik state extract if you want all of a state.
- Because OSM coverage of tiny storefronts is patchy in most US metros and the phone/website tags are rarely both present, use OSM mainly as (a) a cross-check for dedup and (b) a source of `opening_hours`/addresses for demo sites, not as the primary prospect list.
- Store `source = 'osm'` and `source_license = 'ODbL-1.0'` on the row and exclude those rows from any published artefact (client-facing directory, public map), which is what keeps the CRM a non-public Collective/Derivative use.

### Gaps
- taginfo (usage counts for `website` vs `contact:website` and `phone` vs `contact:phone`) and the OSM wiki were blocked; no count of US POIs with a phone tag and no website tag could be measured. Geofabrik's US extract size and update cadence were not verified (the extract is updated daily and is on the order of 10 GB — unverified recollection).

## Q4. Google: websiteUri only as an on-demand check keyed by place_id; Business Profile API is not a prospecting source

### Takeaway
Confirmed from Google's own terms (fetched in the earlier session) and the Business Profile API policy page (secondary this session): Google data may not be bulk-stored or used to build a lead list, only `place_id` may be cached, and the Business Profile APIs exist solely to manage listings you own or are authorized to manage. The correct Google role in this pipeline is a per-row "verify" call: Place Details (New) with field mask `id,websiteUri` for a place_id you resolved from the Overture row, billed at the Enterprise SKU ($20 per 1,000; 1,000 free calls per month).

### Cited Findings
- Maps Platform Terms §3.2.3(a): Customer will not "bulk download ... places information" or "copy and save business names, addresses, or user reviews"; §3.2.3(d)(iii) forbids use "in a listings or directory service or to create or augment an advertising product"; Service Specific Terms §A.3: place_id may be cached (primary, from the existing note) — [Google Maps Platform Terms](https://cloud.google.com/maps-platform/terms); [Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms)
- `websiteUri` sits in the Enterprise SKU of Place Details (New) with `nationalPhoneNumber`, `rating`, `userRatingCount`; Enterprise is $20 per 1,000 at 0-100K volume with 1,000 free calls per month (secondary, from the existing note) — [Place Details (New)](https://developers.google.com/maps/documentation/javascript/place-details); [Google pricing list](https://developers.google.com/maps/billing-and-pricing/pricing)
- Business Profile APIs policy (secondary, search summary of the policy page): "You can only use the Business Profile APIs to create, manage, and report on business listings that you either own or are authorized to manage on behalf of the business owner, or to develop tools for end-clients to similarly manage their listings. Use of the Business Profile APIs for purposes outside the scope of these policies is prohibited."; "Google may deactivate your API project ID if your project is not adhering to Google's API policies." — [Business Profile APIs policies](https://developers.google.com/my-business/content/policies)
- Business Profile eligibility: "lead generation agents or companies are explicitly ineligible for Business Profiles on Google" (secondary, search summary) — [Overview of Google Business Profile policies](https://support.google.com/business/answer/13762416)

### Inferences
- Pipeline role: for each shortlisted Overture row, resolve a place_id with Text Search (New) using `name + formatted address` and an Essentials/Pro field mask (so the search is not billed at Enterprise), store only `place_id`, then call Place Details with `websiteUri` (and optionally `businessStatus`) when the founder opens the record or before an outreach batch. Record your own derived flags (`google_has_website`, `google_checked_at`, `google_status`) in D1; never persist the URL text itself beyond what you re-type by hand into the account record.
- At 1,000 free Enterprise calls per month, Google verification covers ~30 prospects per day at zero cost, which matches a solo founder's outreach rate; a 2,000-row metro backlog costs about $20 if verified in one go.
- The Business Profile API becomes relevant only after the sale, when the client authorizes the agency to manage their profile (then it is the right tool for pushing the new website URL and hours to Google).

### Gaps
- The Business Profile API policy page and the Places (New) policies page were not fetched directly; quotes are search-engine summaries of the Google pages.

## Q5. Secretary of State registries (Georgia, Florida, Texas and others) as a "newly registered, no website yet" signal

### Takeaway
Florida is the standout: the Division of Corporations publishes free daily new-filing files and the full corporate file over a public SFTP account. Georgia sells the full corporations file for $1,000 one-time or $100 setup + $500 per month by FTP, and Texas sells a $20-per-week "new filings" CSV. These give entity name, principal/mailing address, registered agent and filing date, but no phone and no category, so they are a timing signal to join against Overture/Google rather than a standalone prospect list.

### Cited Findings
- Florida (secondary, search summary of dos.fl.gov pages): "The Division of Corporations offers free data downloads for informational purposes. All data downloads are available through your browser or a secure FTP client using Host: https://sftp.floridados.gov, Username: Public" with a public password printed on the page; "Daily files are generated on work days and contain the filings added to our record that day ... ## Q7. Verification and dedup: E.164 phones, candidate-domain probing, search-engine check, expected false-positive rate

### Takeaway
Overture already stores phones in E.164 (`+1904...`), so normalisation is a libphonenumber-js `parse(..., 'US').format('E.164')` pass for the other sources; a cheap three-stage check (DNS lookups of name-derived domains through Cloudflare's DNS-JSON endpoint, a Brave Search query, then the Google `websiteUri` call) can be run from a Worker for well under a cent per row. No published false-positive rate for "no website" flags exists; the measured fact that 52-69 % of flagged rows have a Facebook page, plus the certainty that Overture misses some real sites, means the founder should budget for roughly one quarter to one half of raw flags being wrong until the first 200 rows are hand-verified (estimate).

### Cited Findings
- libphonenumber (primary): "Google's common Java, C++ and JavaScript library for parsing, formatting, and validating international phone numbers"; E.164 format "Produces '+41446681800'"; `isPossibleNumber` "quickly guesses whether a number is a possible phone number by using only the length information"; `isValidNumber` is "full validation of a phone number for a region using length and prefix information"; JS ports: "libphonenumber-js - a stripped-down rewrite, about 110 KB in size" and "google-libphonenumber ... about 420 KB" — [google/libphonenumber README](https://raw.githubusercontent.com/google/libphonenumber/master/README.md)
- Overture phones are already E.164 in the data (measured, e.g. `+19042894720`) — [release on S3](https://overturemaps-us-west-2.s3.amazonaws.com/?list-type=2&prefix=release/2026-09-23.1/theme=places/type=place/)
- Cloudflare DNS over HTTPS JSON API (primary): endpoint "https://cloudflare-dns.com/dns-query", header `accept: application/dns-json`, parameters `name` and `type` (default A); response carries `Status` ("The Response Code of the DNS Query") and `Answer[]` with `name`, `type`, `TTL`, `data` — [Cloudflare docs: dns-json](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json.mdx)
- Brave Search API pricing (secondary): Search plan "$5 per 1,000 requests"; the 5,000-free-queries plan was withdrawn for new users by February 2026, replaced by "$5 in monthly credits (roughly 1,000 queries)" — [Costbench Brave Search API pricing](https://costbench.com/software/ai-search-apis/brave-search-api/); [Costbench free plan](https://www.costbench.com/software/ai-search-apis/brave-search-api/free-plan/)
- Google Place Details `websiteUri` is Enterprise SKU, $20 per 1,000 with 1,000 free per month (Q4)
- Workers limits relevant to running the checks (primary): subrequests 50 per request on Free, "10,000 (up to 10M)" on Paid; CPU 10 ms (Free) vs "5 min (default: 30 seconds)" (Paid) per request; Cron Triggers 5 per account Free / 250 Paid; cron handlers get "30 seconds (< 1 hour interval)" or "15 min (>= 1 hour interval)" CPU and a 15-minute wall-clock cap; 128 MB memory per isolate — [Workers limits](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/workers/platform/limits.mdx)
- Dedup rules (from the existing note Q8): exact `(channel, external_id)`, then E.164 phone, then website host / email domain, then `name_norm` + postcode, then fuzzy name within ~500 m surfaced for human confirmation — [existing note Q8](../Local%20storefront%20platform%20strategy/admin_dashboard_and_leads.md)
- Survey baseline for the true no-website rate (17-27 % of small businesses, 2025) vs the measured Overture flag rate (20.7 % of US rows with no website; 13.8 % phone-and-no-website) — [Clutch via BusinessWire](https://www.businesswire.com/news/home/20250821848152/en/Clutch-Report-No-Code-Tools-Fuel-Website-Growth-Yet-17-of-Small-Businesses-are-Still-Offline)

### Inferences
- Verification ladder (cheapest first, stop at the first positive), implemented as a Workflow step per row so it can retry and sleep:
  1. Normalise: `phone_e164` via libphonenumber-js (`isValidNumber` for US); `name_norm` per the existing note; split `addresses[0]` into street/locality/region/postcode.
  2. Presence from the row itself: if `socials` contains a facebook/instagram URL set `presence='social_only'`; if `emails` has a non-webmail domain (not gmail/yahoo/outlook/aol/icloud) that domain is almost certainly a live website; probe it first.
  3. Domain probing: generate 6-10 candidates from `name_norm` (`{slug}.com`, `{slug}.net`, `{slug}.co`, `{slug}{city}.com`, `{slug}-{city}.com`, initials+city) and resolve each with the DNS-JSON endpoint (`Status 0` and an A/AAAA/CNAME answer). For hits, do a 5-second HEAD/GET from the Worker and accept only if the HTML title or body contains the business name or phone (parked pages and unrelated namesakes are common). Cost: zero; ~10 subrequests per row.
  4. Search check: one Brave query `"{name}" {city} {state}`; collect result hosts; strip a deny-list (facebook, instagram, yelp, google, mapquest, yellowpages, bbb, nextdoor, linkedin, doordash, grubhub, ubereats, squareup, toasttab, linktr.ee, etc.); any remaining host whose page mentions the phone number is a website hit; a Square/Toast/Linktree hit is `presence='ordering_page'`. Cost about $0.005 per row.
  5. Google check: Text Search (New) to get `place_id`, Place Details `websiteUri`; this is the authoritative "Google shows a website" answer and the one the prospect will judge you by. Cost $0.02 per row beyond the 1,000 free monthly calls.
  6. Human check: the founder opens the Facebook page and the Google listing before sending anything (also catches closed businesses, which neither Overture's `operating_status` nor the search reliably flags).
- Expected false-positive rate: unmeasured in the literature. Components: (a) Overture lacks a website that exists (the provider union helps, but Meta-sourced rows only know what the owner typed into the Facebook page) - estimate 10-25 % of flags; (b) "no website" but an ordering page / marketplace / Linktree that the owner treats as their site - estimate 5-10 %; (c) closed or moved businesses that pass the open+confidence filter - the measured `permanently_closed` rate is 2-4 % and null-status rows are 25 %, so estimate another 5-10 % dead rows. Combined, expect 20-40 % of raw flags to be non-prospects (estimate); the ladder above should cut that to under 10 % before a human sees the row. Measure it on the first 200 rows and store the outcome as `verify_result` so the thresholds can be tuned per metro.
- Throughput: with Paid Workers the whole ladder is ~15 subrequests per row, so a 2,000-row metro verifies in a single Workflow run of 2,000 steps (under the 10,000-step Paid limit from the existing note Q10) with no cost beyond Brave/Google calls (~$10 + $20 if every row reaches Google).

### Gaps
- No empirical study of "no website" flag precision for Overture/FSQ was found; the percentages above are estimates to be replaced by the founder's own first-200 measurement.
- Brave's current terms on storing result URLs and the exact credit mechanics were not verified from Brave's site (blocked); Bing Web Search was not evaluated (retired in 2025 per general knowledge, unverified).

## Q8. Legal summary for storing these rows and contacting the businesses

## Q9. Sample DuckDB SQL for a metro slice, Worker/Workflow design to load D1, expected counts

### Takeaway
One DuckDB statement over the public Overture bucket produces the metro candidate file (a few thousand rows) in seconds; the load path that respects Cloudflare's limits is "DuckDB on a laptop or a monthly GitHub Actions job -> CSV/SQL in R2 -> Cloudflare Workflow upserts into D1 in 50-row batches", with Workers cron used only to kick the Workflow and to run the nightly hygiene/verification jobs.

### Cited Findings
- DuckDB prerequisites and the performance notes (primary) — [OvertureMaps/docs duckdb.mdx](https://raw.githubusercontent.com/OvertureMaps/docs/main/docs/getting-data/duckdb.mdx)
- D1 import path (primary): `npx wrangler d1 execute <database> --remote --file=<file.sql>`; "'wrangler d1 execute --file' is limited to 5GiB files, the same as the R2 upload limit"; "For imports larger than 5GiB, we recommend splitting the data into multiple files"; on "Statement too long" "convert the single large INSERT statement into multiple smaller INSERT statements"; `PRAGMA defer_foreign_keys = true` for ordered imports — [D1 import/export](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/d1/best-practices/import-export-data.mdx)
- D1 limits (from the existing note Q8): 100 bound parameters per query, 100 KB per SQL statement, 1,000 queries per Worker invocation on Paid, 10 GB per database on Paid — [D1 limits](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/d1/platform/limits.mdx)
- Workflows limits (existing note Q10): Paid 30 s CPU per step, 10,000 steps per instance (up to 25,000), `step.sleep` up to 365 days, 10,000 subrequests per instance — [Workflows limits](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/workflows/reference/limits.mdx)
- Cron handler caps (primary): 15-minute wall clock, 30 s / 15 min CPU depending on interval; 5 crons per account on Free, 250 on Paid — [Workers limits](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/workers/platform/limits.mdx)
- Measured counts (Q2): Chattanooga-area bbox 27,381 rows -> 3,347 phone/no-website -> 2,665 open+conf>=0.5 -> 1,848 at conf>=0.75; Jacksonville-area bbox 78,652 -> 10,656 -> 8,144 -> 4,983; query time 3.7-4.6 s per metro from a sandbox with pyarrow row-group pruning on `bbox` — [release on S3](https://overturemaps-us-west-2.s3.amazonaws.com/?list-type=2&prefix=release/2026-09-23.1/theme=places/type=place/)

### Inferences
- DuckDB SQL for one metro (predicates validated with pyarrow against the same files in this session; DuckDB extension install itself could not run in the sandbox, so run this on a laptop or CI runner):

```sql
INSTALL spatial; LOAD spatial;
INSTALL httpfs;  LOAD httpfs;
SET s3_region = 'us-west-2';
-- anonymous read of the public bucket (no credentials needed)
SET VARIABLE xmin = -85.45; SET VARIABLE ymin = 34.90;
SET VARIABLE xmax = -84.95; SET VARIABLE ymax = 35.25;   -- Chattanooga-area bbox

COPY (
  SELECT
    id                                   AS overture_id,
    names.primary                        AS name,
    phones[1]                            AS phone_e164,      -- already E.164 in the data
    list_transform(socials, s -> s)      AS socials,
    emails[1]                            AS email,
    addresses[1].freeform                AS street,
    addresses[1].locality                AS city,
    addresses[1].region                  AS region,
    addresses[1].postcode                AS postcode,
    taxonomy.primary                     AS category,
    confidence,
    operating_status,
    sources[1].dataset                   AS source_dataset,
    sources[1].license                   AS source_license,
    sources[1].record_id                 AS source_record_id,
    sources[1].update_time               AS source_updated_at,
    ST_Y(ST_GeomFromWKB(geometry))       AS lat,
    ST_X(ST_GeomFromWKB(geometry))       AS lng
  FROM read_parquet('s3://overturemaps-us-west-2/release/2026-09-23.1/theme=places/type=place/*.parquet')
  WHERE bbox.xmin >= getvariable('xmin') AND bbox.xmax <= getvariable('xmax')
    AND bbox.ymin >= getvariable('ymin') AND bbox.ymax <= getvariable('ymax')
    AND addresses[1].country = 'US'
    AND len(phones) > 0
    AND (websites IS NULL OR len(websites) = 0)
    AND (operating_status IS NULL OR operating_status = 'open')
    AND confidence >= 0.5
    AND taxonomy.primary NOT IN ('christian_place_of_worship','baptist_place_of_worship','religious_organization',
                                 'real_estate_agent','real_estate_service','historic_site','government_office',
                                 'social_or_community_service','school','cemetery')
) TO 'prospects_chattanooga_2026-09-23.1.csv' (HEADER, DELIMITER ',');
```

  For a statewide or nationwide run replace the bbox with `addresses[1].region = 'TN'` (slower: no row-group pruning) or loop over a list of metro bboxes. Equivalent FSQ SQL, once access is restored (unverified path): `FROM read_parquet('s3://fsq-os-places-us-east-1/release/dt=2026-09-15/places/parquet/*.parquet') WHERE country='US' AND tel IS NOT NULL AND website IS NULL AND date_closed IS NULL AND latitude BETWEEN ... AND longitude BETWEEN ...`.
- Load design (fits the limits above):
  1. Monthly GitHub Actions job (or the founder's laptop) runs the DuckDB script per metro, writes `prospects_<metro>_<release>.csv` to R2 via `wrangler r2 object put` or the S3 API, then calls an admin endpoint that starts a `ProspectImport` Workflow with `{metro, release, r2_key}`.
  2. Workflow `step.do('manifest')` reads the CSV from R2 and splits it into 50-row chunks (50 rows x ~18 columns stays well under 100 bound parameters per statement when each row is its own prepared statement inside one `db.batch()` of 50 statements, and under 1,000 queries per invocation).
  3. `step.do('chunk-i')` upserts: `INSERT INTO accounts (id, name, name_norm, phone_e164, street, city, region, postal, lat, lng, source, source_ref, source_license, source_release, website_url) VALUES (...) ON CONFLICT(source, source_ref) DO UPDATE SET ...` plus `INSERT OR IGNORE INTO channel_listings(channel='overture', external_id=overture_id, ...)`; rows whose E.164 phone already exists on another account are routed to the dedup queue instead of inserted (rule 2 of the existing note).
  4. `step.do('verify-i')` runs the Q7 ladder for new rows only, recording `presence`, `verify_result`, `verified_at`; `step.sleep` between Brave/Google batches keeps within API quotas.
  5. A cron (`0 9 * * 1`, Paid plan) starts a `WeeklyHygiene` Workflow: null Google lat/lng older than 30 days, re-check `do_not_contact`, expire rows that failed verification twice, and pull the Florida daily SOS files for the last 7 days into `accounts(source='fl_sos')`.
  6. Why not do the DuckDB step in a Worker: cron handlers are capped at 15 minutes and 128 MB and cannot run DuckDB; the parquet scan belongs off-platform, and only the few-thousand-row result crosses into Cloudflare.
- Expected counts per load: mid-sized metro ~2,500 candidate rows before category pruning, ~1,500-2,000 after (estimate from the Chattanooga measurement); large metro (Jacksonville-sized) ~8,000 before pruning; nationwide ~1.9 M at confidence >= 0.5 or ~1.2 M at >= 0.75 (estimate = 16 x the sampled counts 116,585 / 75,841). A nationwide table of 1.9 M rows x ~0.5 KB is ~1 GB, inside D1's 10 GB Paid limit but far more than a solo founder can work; load metros on demand instead.
