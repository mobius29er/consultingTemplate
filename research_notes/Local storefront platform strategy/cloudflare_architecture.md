## Key Question 1: Workers for Platforms (dispatch namespaces) — what it is, 2026 pricing, limits, dynamic dispatch, and whether "one Worker per client site" or "one shared multi-tenant Worker" is the right primitive

### Takeaway
Workers for Platforms (WfP) is a $25/month add-on that gives you an unlimited number of isolated "user Workers" in a dispatch namespace plus a "dispatch Worker" that routes each request (typically by hostname) with `env.DISPATCHER.get(name)`; it is the right primitive once you have more than a few hundred per-client Workers or need per-tenant resource limits, but for the first ~100 to 400 sites a solo developer can run "one standard Worker per client site" on the $5 Workers Paid plan (500-Worker cap) and move to WfP later with the same Astro build output.

### Cited Findings
- WfP Paid plan is "$25 monthly", with "20 million requests included per month" (+$0.30 per additional million), "60 million CPU milliseconds included per month" (+$0.02 per additional million CPU ms), "1000 scripts" included then "+$0.02 per additional script"; subrequests are not billed; CPU across dispatch Worker → user Worker → outbound Worker is charged as a single request — [Workers for Platforms pricing](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/pricing/)
- "Cloudflare provides an unlimited number of scripts for Workers for Platforms customers"; WfP accounts "do not have a limit for the number of Durable Object namespaces"; default cache is disabled for namespaced scripts to maintain isolation; "You can set a maximum of eight tags per script"; gradual deployments are not yet supported for user Workers; user Workers cannot access the `cf` object unless trusted mode is enabled for the namespace — [Workers for Platforms limits](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/limits/)
- Standard Workers limits: "Workers per account | 100 (Free) | 500 (Paid)", with the footnote "If you need a higher Worker limit, use Workers for Platforms"; "Routes per zone: 1,000"; "Custom domains per zone: 100"; "If you require more than 100 custom domains per zone, consider using a wildcard route" — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- A dispatch namespace "serves as a container for all customer Workers"; best practice is "All your customers' Workers should live in a single namespace (for example, `production`)"; user Workers run in untrusted mode by default, "never share a cache even when running on the same Cloudflare zone, and cannot access the `request.cf` object"; user Workers can be given "KV, D1, R2, and other Cloudflare resources" via bindings; guidance: "Use Service bindings when you know exactly which Workers need to communicate. Use Workers for Platforms when user Workers are uploaded dynamically by your customers." — [How Workers for Platforms works](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/how-workers-for-platforms-works/)
- Dispatch Worker binding in `wrangler.jsonc`: `"dispatch_namespaces": [{ "binding": "DISPATCHER", "namespace": "my-dispatch-namespace" }]`; invocation: `const userWorker = env.DISPATCHER.get("user-worker", { props: { userId, permissions } }); return userWorker.fetch(request);`; outbound parameters are passed as a third argument `env.DISPATCHER.get("user-worker", { props: {...} }, { outbound: { requestContext: {...} } })`; when the script does not exist the error message is `"Worker not found"` — [Dynamic dispatch](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/dynamic-dispatch/)
- Per-tenant resource caps: `dispatcher.get()` accepts `limits: { cpuMs: 10, subRequests: 5 }`; example tiers `enterprise: { cpuMs: 50, subRequests: 50 }, pro: { cpuMs: 20, subRequests: 20 }, free: { cpuMs: 10, subRequests: 5 }`; "If a user Worker hits either of these limits, the user Worker will immediately throw an exception" — [Custom limits](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/platform/custom-limits/) (secondary: search snippet)
- Hostname routing recipe: configure Cloudflare for SaaS custom hostnames, set a fallback origin, CNAME customer DNS to your SaaS domain, add a `*/*` route on the platform zone bound to the dispatch Worker, then route in code: `const hostname = new URL(request.url).hostname; const hostnameData = await env.KV.get(\`hostname:${hostname}\`, { type: "json" }); const userWorker = env.DISPATCHER.get(hostnameData.workerName); return await userWorker.fetch(request);`; the `*/*` wildcard route "works regardless of how DNS is configured"; routing on custom-hostname custom metadata requires subdomains created as custom hostnames — [Hostname routing](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/hostname-routing/)
- Outbound Workers "sit between your customer's Workers and the public Internet" and "give you visibility into all outgoing `fetch()` requests from user Workers"; configured as `"outbound": { "service": "<SERVICE_NAME>", "parameters": ["params_object"] }` on the `dispatch_namespaces` binding; use cases are request logging, hostname allow/block lists, and injecting API authentication — [Outbound Workers](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/outbound-workers/)
- User Workers in a dispatch namespace can carry static assets (i.e. an Astro build): three-step upload (assets-upload-session with manifest of SHA-256 hashes/sizes → upload files with the returned JWT → PUT the script with the completion JWT), or simply `npx wrangler deploy --name <USER_WORKER_NAME> --dispatch-namespace <NAMESPACE_NAME>`; asset hashing is namespace-scoped so identical files are shared across Workers — [Static assets in Workers for Platforms](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/static-assets/)
- Workers Paid plan: "$5 USD per month for an account", "10 million included per month" requests (+$0.30/M), "30 million CPU milliseconds included per month" (+$0.02 per additional million CPU ms); "Requests to static assets are free and unlimited" on both Free and Paid — [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)

### Inferences
- Pattern A, "one shared multi-tenant Worker" (single Astro codebase that resolves tenant from `request.url.hostname` → D1/KV config): cheapest ($5/mo total compute), one `wrangler deploy` pushes template updates fleet-wide, but blast radius is every client at once, per-client custom code is impossible (only data-driven customization), the Astro build must prerender nothing tenant-specific (SSR per request), and handoff requires extracting a tenant into a standalone project.
- Pattern B, "one Worker per client site" as standard Workers on Workers Paid: each client gets its own Astro build, bindings, secrets, and workers.dev preview; blast radius is one site; template updates are a fleet rebuild/redeploy loop (CI matrix); the hard caps that bite are 500 Workers/account, 100 custom domains per zone, and 250 cron triggers per account (see Q7). This is the natural fit for a developer already shipping Astro-on-Workers sites.
- Pattern C, "one user Worker per client site inside a WfP dispatch namespace": same per-site builds as B, deployed with `wrangler deploy --dispatch-namespace production`, unlimited scripts, tags for customer metadata, per-tenant CPU/subrequest caps, outbound control, and a dispatch Worker that maps hostname → script (KV lookup). Costs $25/mo more than B. Dispatch Worker becomes the single entry point for both `clientslug.preview.yourbrand.com` and client custom hostnames.
- Recommended sequence: start on Pattern B (zero new concepts, matches current stack), keep a strict naming convention (`site-<slug>`), keep per-tenant data in a per-client D1, and migrate to Pattern C when you approach ~100 sites on the preview zone (custom-domain cap) or want per-tenant limits; the Astro build output and bindings are identical in B and C, only the deploy command and the routing layer change.
- Because the default cache is disabled for namespaced scripts and user Workers cannot see `request.cf`, geolocation/caching features of the Astro site would need trusted mode or must be done in the dispatch Worker.

### Gaps
- WfP limits page does not state per-user-Worker script size, binding count, or CPU limits; the standard Workers limits presumably apply but this was not confirmed on the WfP pages.
- Whether "trusted mode" is self-serve or requires contacting Cloudflare was not confirmed (the how-it-works page only discusses untrusted mode).

## Key Question 2: Cloudflare for SaaS (custom hostnames / SSL for SaaS) — pricing, how a client points their domain, fallback origin, validation flow, wildcards, interaction with Workers / WfP

### Takeaway
Cloudflare for SaaS gives every plan (including Free) 100 custom hostnames at no cost and $0.10/hostname/month after that; a client keeps DNS at their registrar and adds a CNAME to your fallback-origin hostname, Cloudflare issues the certificate (HTTP or TXT validation), and a `*/*` Worker route on your SaaS zone makes your Worker (or dispatch Worker) the origin — this is the "go live on the client's domain without moving accounts" mechanism, with apex (non-www) domains and wildcards being the sharp edges.

### Cited Findings
- Plan table: Free, Pro and Business all include "100" custom hostnames, "$0.10" per additional hostname, "Max hostnames 50,000"; Enterprise is custom; "Custom origin" and "Custom analytics" are available on all plans; "Wildcard custom hostnames", "Custom certificates", "CSR support", "Selectable CA", "SNI Rewrite for Custom Origin", "mTLS support" are Enterprise-only; "Apex proxying/BYOIP" and "Custom metadata" are paid add-ons — [Cloudflare for SaaS plans](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/plans/)
- The feature works "on a Free plan" zone; the first step is to set a fallback origin ("Existing custom hostname traffic continues to flow while the fallback origin is updated"); create hostnames via dashboard or `POST /zones/{zone_id}/custom_hostnames` with an `ssl` object specifying validation method (`txt` or `http`) and type `dv`; customers "point their domain using a CNAME record targeting your CNAME target subdomain (e.g., `customers.saasprovider.com`)"; "If your customer needs to use an A record...you will need to get apex proxying"; a hostname is production-ready when `result.status = active` (hostname validated) and `result.ssl.status = active` (certificate issued) and DNS points correctly — [Cloudflare for SaaS getting started](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/getting-started/)
- Using a Worker as the fallback origin: create an originless DNS record "service.example.com AAAA 100::" and a Worker route of "`*/*`" which "routes all traffic entering your zone to the Worker, including requests from custom hostnames"; caveat: when a Worker route matches, "the `custom_origin_server` setting on individual custom hostnames is bypassed because the Worker processes the request before origin resolution occurs", so per-hostname routing must be done inside the Worker using the Host header or custom metadata — [Worker as origin for Cloudflare for SaaS](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/advanced-settings/worker-as-origin/)
- WfP hostname-routing doc confirms the same stack: SaaS custom hostnames → fallback origin → CNAME → `*/*` route to the dispatch Worker → hostname lookup in KV — [Hostname routing](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/hostname-routing/)
- Workers (not Pages) require the custom domain's zone to be on Cloudflare nameservers; Pages' listed advantage is "Custom domains outside Cloudflare zones" — [Migrate from Pages](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/)

### Inferences
- Two ways to put a client's domain in front of a Worker in your account: (1) add the client's domain as a regular zone in your account (free plan), point the registrar's nameservers to Cloudflare, then use a Workers Custom Domain or route — no SaaS feature needed, full DNS control, but it couples the client's DNS to your account; (2) leave DNS at the client's registrar and use Cloudflare for SaaS custom hostnames with a CNAME — looser coupling, better for handoff, and free for the first 100 hostnames. For a managed service, (2) is cleaner; for clients who want "you handle everything", (1) is simpler.
- Apex domains (`joespizza.com` rather than `www.joespizza.com`) only work with the CNAME method if the client's DNS host supports CNAME flattening/ALIAS at the apex; otherwise apex proxying is an Enterprise add-on. Practical rule: make `www.` canonical, create the custom hostname for `www.<domain>`, and have the client set an apex redirect at their registrar — or move DNS to a Cloudflare zone (which flattens apex CNAMEs).
- Because custom metadata on hostnames is a paid add-on and wildcards are Enterprise-only, the hostname → tenant mapping should live in your own KV/D1 (as the Cloudflare recipe shows), and each client hostname (www and apex) is created individually.
- HTTP validation completes automatically once the CNAME resolves through Cloudflare; TXT validation lets you pre-validate before DNS cutover (zero-downtime migration from an existing site) but requires the client to add a TXT record. The dashboard should offer both and poll `ssl.status`.

### Gaps
- Whether enabling Cloudflare for SaaS on a Free zone still requires a one-time dashboard enablement step or a payment method on file was not confirmed in this run.
- Exact certificate-validation status strings beyond `active` (e.g. `pending_validation`, `pending_issuance`) were not captured; see the custom hostnames API reference.

## Key Question 3: Workers Static Assets vs Cloudflare Pages — Pages status in 2025-2026, what Astro's adapter targets now, preview URLs and per-prospect demo URLs

### Takeaway
Cloudflare's own docs now say "Start new projects with Workers"; Pages is not sunset but gets no new features, and the Astro Cloudflare adapter (v13+ for Astro 6, v14.x in 2026) deploys to Workers only with static assets. Every Worker gets a `workers.dev` URL and per-version/aliased preview URLs, and a per-prospect `clientslug.preview.yourbrand.com` is either a Workers Custom Domain (capped at 100 per zone) or a wildcard route to a router/dispatch Worker (uncapped).

### Cited Findings
- Banner on the Pages docs: "Workers supports most Pages use cases and offers a broader feature set. It is Cloudflare's primary platform for building applications. Start new projects with Workers." — [Cloudflare Pages docs (banner partial `workers-for-new-projects`)](https://developers.cloudflare.com/pages/)
- The migration guide lists Workers-only capabilities: Workers Logs, Logpush, Tail Workers, Source Maps, Cron Triggers, Durable Objects, Email Workers, Image Resizing, Queue consumers, Rate Limiting bindings, Vite plugin, Gradual Deployments, Remote Development; Pages' remaining advantages are "Custom domains outside Cloudflare zones", "Branch Deploy Controls" and simpler file-based routing; framework guidance: "Switch out any Pages-specific adapters for the Workers equivalent" — [Migrate from Pages to Workers](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/)
- Cloudflare's April 8, 2025 announcement made static sites and full-stack apps on Workers GA (Astro among supported frameworks); Cloudflare is not sunsetting Pages but is turning Pages-specific features into general Workers features; existing Pages projects remain supported — [Full-stack development on Cloudflare Workers (blog, Apr 2025)](https://blog.cloudflare.com/full-stack-development-on-cloudflare-workers/) (secondary: search snippet); community summary: "Pages is not officially deprecated and will continue to be supported and receive bug fixes... all new investment goes to Workers" — [Cloudflare Pages vs Workers in 2026](https://www.morphllm.com/comparisons/cloudflare-pages-vs-workers) (secondary)
- Workers Sites (the older asset mechanism) is deprecated in favor of Workers Static Assets — [Wrangler deprecations](https://developers.cloudflare.com/workers/wrangler/deprecations/) (secondary: search snippet)
- Astro adapter: "requires v13 or later" for Astro 6; "deploys to Cloudflare Workers only. Support for Cloudflare Pages has been removed"; required `wrangler.jsonc`: `"main": "@astrojs/cloudflare/entrypoints/server"`, `"assets": { "directory": "./dist", "binding": "ASSETS" }`, `"compatibility_flags": ["nodejs_compat"]`, `"compatibility_date": "2024-09-23"` or later; sessions use KV automatically via the `SESSION` binding (`sessionKVBindingName` to rename); default `imageService` is `'cloudflare-binding'` with options `compile`, `cloudflare`, `passthrough`, `custom`, or an object `{ build: 'compile', runtime: 'cloudflare-binding' }`; Astro 6 removed `Astro.locals.runtime` (use `import { env } from 'cloudflare:workers'`), `workerEntryPoint` and `cloudflareModules`; prerendered pages run in `workerd` by default (`prerenderEnvironment: 'node'` to opt out); env-specific deploys use `CLOUDFLARE_ENV=some-env astro build && wrangler deploy` — [Astro Cloudflare adapter docs](https://docs.astro.build/en/guides/integrations-guide/cloudflare/)
- `@astrojs/cloudflare@14.2.0` adds opt-in build-time image optimization via the Cloudflare `IMAGES` binding in the workerd prerender environment, lets `session: false` tree-shake the KV session driver, and supports Astro's experimental incremental builds — [@astrojs/cloudflare 14.2.0 release](https://newreleases.io/project/github/withastro/astro/release/@astrojs%2Fcloudflare@14.2.0) (secondary)
- Preview URL format for both kinds: `<VERSION_PREFIX OR ALIAS>-<WORKER_NAME>.<SUBDOMAIN>.workers.dev`; `wrangler versions upload` returns a versioned preview URL; `wrangler versions upload --preview-alias staging` creates `staging-<WORKER_NAME>.<SUBDOMAIN>.workers.dev`; aliases are lowercase letters/numbers/dashes, start with a letter, and alias + worker name must fit in 63 characters — [Workers preview URLs](https://developers.cloudflare.com/workers/versions-and-deployments/preview-urls/) (secondary: search snippet; the doc source path had moved and could not be fetched)
- Workers Builds (git-connected CI): "3,000 per month" build minutes free, "6,000 per month (then, +$0.005 per minute)" on paid, 1 vs 6 concurrent builds — [Workers Builds limits and pricing](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/)
- Static assets limits: "Files per Worker version | 20,000 (Free) | 100,000 (Paid)", "Individual file size | 25 MiB" — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

### Inferences
- The developer's existing stack (Astro + `@astrojs/cloudflare` + Workers static assets + `wrangler deploy`) is exactly what Cloudflare is steering everyone toward; nothing to migrate.
- Demo-URL options, cheapest first: (a) the free `site-<slug>.<yoursubdomain>.workers.dev` URL (zero config, looks unbranded); (b) `wrangler versions upload --preview-alias demo` for throwaway revisions; (c) a branded `<slug>.preview.yourbrand.com` via Workers Custom Domains until the 100-per-zone cap; (d) a wildcard route `*.preview.yourbrand.com/*` on one router (or dispatch) Worker that maps the subdomain to the site Worker via service binding / dispatch namespace — uncapped and the only option that scales past 100 prospects.
- Preview URLs on `workers.dev` are public by default; gate prospect demos with Cloudflare Access (free for 50 users, see Q5) or a shared-secret query param set by the dashboard if you do not want them indexable.

### Gaps
- Whether preview URLs are enabled by default on new Workers and whether Workers Builds generates per-pull-request preview URLs could not be confirmed from the fetched sources.
- The exact mapping "Astro 7 ↔ `@astrojs/cloudflare` 14.x" was not confirmed from the Astro docs (the docs page fetched discusses Astro 6 / adapter v13+; the 14.2.0 release exists per a secondary source).

## Key Question 4: D1 (limits, pricing, replication, per-tenant vs shared, FTS5) and the other primitives relevant to this use case (KV, R2, Queues, Cron, Workflows, Durable Objects, Email, Images, Turnstile)

### Takeaway
D1 is explicitly designed for "per-tenant" databases: 50,000 databases per paid account, 10 GB each, 25 billion reads and 5 GB storage included for $5/month, FTS5 supported — so one D1 per client site is the right default (clean export for handoff, isolated blast radius), with the caveat that FTS5 virtual tables block D1 export.

### Cited Findings
- D1 limits: "Databases per account: 50,000 (Workers Paid) / 10 (Free)"; "Maximum database size: 10 GB (Workers Paid) / 500 MB (Free)"; "Maximum storage per account: 1 TB (Workers Paid) / 5 GB (Free)"; "Maximum number of columns per table: 100"; "Queries per Worker invocation: 1,000 (Workers Paid) / 50 (Free)"; "Maximum SQL query duration: 30 seconds"; "Time Travel duration: 30 days (Workers Paid) / 7 days (Free)"; "Maximum bindings per Workers script: Approximately 5,000"; "Maximum file import size: 5 GB"; the 10 GB per-database limit "cannot be further increased"; D1 "is designed for horizontal scale out across multiple, smaller (10 GB) databases, such as per-user, per-tenant or per-entity databases" — [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
- D1 pricing (Workers Paid): "first 25 billion rows read per month" included then $0.001 per million, "first 50 million rows written per month" included then $1.00 per million, "first 5 GB of storage included plus $0.75 per GB-month"; D1 bills only on rows read/written and storage above the included limit, "not billed for hours or capacity units" — [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) (figures via search snippet of the same page; concept text from page source)
- Read replication: public beta since April 2025 via the Sessions API; "read replication does not charge extra for read replicas"; replicas are created automatically "(currently one in each supported D1 region)" and routed transparently; sessions are "sequentially consistent" — [D1 read replication beta changelog](https://developers.cloudflare.com/changelog/post/2025-04-10-d1-read-replication-beta/) and [D1 FAQ](https://developers.cloudflare.com/d1/reference/faq/) (secondary: search snippets; GA status not confirmed)
- FTS5: D1 supports SQLite's FTS5 module (including `fts5vocab`) as a supported extension; "Export is not supported for virtual tables, including databases with virtual tables" — [D1 SQL statements](https://developers.cloudflare.com/d1/sql-api/sql-statements/) (secondary: search snippet)
- Moving D1 data: `POST /accounts/{account_id}/d1/database/{database_id}/export` returns a URL to download the SQL, during which "your D1 will be unavailable to serve queries"; import via `wrangler d1 execute --file` (5 GiB limit per file) — [D1 export API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/) and [D1 import/export](https://developers.cloudflare.com/d1/best-practices/import-export-data/) (secondary: search snippets)
- KV (paid): $0.50/GB-month storage, $0.50 per million reads, $5.00 per million writes/deletes/lists; R2: $0.015/GB-month, zero egress, Class A ops $4.50 per million; Queues: $0.40 per million operations, 10,000 ops/day free — [Cloudflare Workers pricing calculator / Workers pricing](https://makerkit.dev/pricing-calculator/cloudflare) and [workers.cloudflare.com pricing](https://workers.cloudflare.com/pricing/) (secondary); R2 standard storage "$0.015/GB-month" with free egress also stated on the Workers pricing page — [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)
- Cron Triggers: "Number of Cron Triggers per account | 5 (Free) | 250 (Paid)"; "CPU time per Cron Trigger | 10 ms | 30 seconds (< 1 hour interval), 15 min (>= 1 hour interval)" — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Email: MailChannels' free Workers sending API was terminated (announced for June 30, 2024; unavailable from August 31, 2024) — [MailChannels end-of-life notice](https://support.mailchannels.com/hc/en-us/articles/26814255454093-End-of-Life-Notice-Cloudflare-Workers); Cloudflare Email Service outbound sending is "Workers Paid plan only": "3,000 included per month, then $0.35 per 1,000 emails"; inbound Email Routing is "Unlimited" on Free and Paid; "Sends to verified destination addresses are free and do not count toward the included quota" — [Email Service pricing](https://developers.cloudflare.com/email-service/platform/pricing/); limits: 5 MiB message (25 MiB to verified destinations), "50 per email" recipients, "30" combined Email Routing/Sending domains per zone, "New accounts start with a conservative daily quota and scale up over time"; "Before you onboard a sending domain, you can send emails only to verified destination addresses in your account" — [Email Service limits](https://developers.cloudflare.com/email-service/platform/limits/); `send_email` binding supports `destination_address` or `allowed_destination_addresses` restrictions — [Send bindings](https://developers.cloudflare.com/email-service/configuration/send-bindings/) (secondary)
- Cloudflare Images: "first 5,000 unique transformations included for free", then "$0.50 per 1,000 unique transformations per month", billed per unique image+options combination; stored images "$5 per 100,000 images stored per month and $1 per 100,000 images delivered per month"; transforming images stored elsewhere bills only transformations — [Images pricing](https://developers.cloudflare.com/images/pricing/) (secondary: search snippet); a July 1, 2026 changelog concerns how the Images binding counts unique transformations — [2026-07-01 changelog](https://developers.cloudflare.com/changelog/post/2026-07-01-binding-unique-transformations/) (not fetched)
- Turnstile: free, "unlimited challenges and up to 20 widgets per account", 7-day analytics on the free plan; Enterprise for unlimited widgets — [Turnstile plans](https://developers.cloudflare.com/turnstile/plans/) (secondary: search snippet)
- Workers Paid also raises "Subrequests per invocation | 50 (Free) | 10,000 (up to 10M) (Paid)", "Variables per Worker (secrets + text) | 64 | 128", "Memory per isolate | 128 MB", "Worker size (uncompressed) | 64 MiB" — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

### Inferences
- One D1 per client site is the right default: 50,000 databases is effectively unlimited for this business, storage is pooled against the 5 GB included allowance (a brochure/storefront DB is tens of MB), per-client export gives a clean handoff artifact, and a bad migration only breaks one client. A shared D1 with `tenant_id` saves nothing on cost and makes handoff and blast radius worse; the only reason to share is cross-tenant reporting, which the admin dashboard can do by querying each DB or by writing summary rows to a central "platform" D1.
- The admin dashboard's own data (customers, sites, deployments, hostnames, Stripe subscription state) belongs in a single "platform" D1 that links `customer_id` → `worker_name`/`script_name`, `d1_database_id`, `kv_namespace_id`, `custom_hostname_id`, `preview_url`.
- FTS5 is available for on-site search (menus, products), but because databases containing virtual tables cannot be exported, the handoff/export routine must drop FTS tables (or keep FTS in a separate D1) and rebuild them after import.
- Email for contact forms: cheapest reliable path on Workers today is Cloudflare Email Service (3,000/month included on Paid; sends to verified addresses are free, but every client's inbox would need to be a verified destination in your account) or a third-party API (Resend/Postmark) over HTTPS — there is no SMTP from Workers.
- Cron: 250 per paid account is the first fleet limit you will hit if every client site registers its own cron; centralize scheduled work in one platform Worker (or Workflows/Queues) that iterates tenants.
- Images: the adapter's default `cloudflare-binding` runtime service means 5,000 free unique transformations per month across all sites, then $0.50/1,000; switching to `{ build: 'compile' }` (build-time Sharp) makes image cost zero at the expense of build time.

### Gaps
- Whether D1 read replication reached GA by October 2026 was not confirmed; last known status is public beta (April 2025) at no extra charge.
- Durable Objects, Workflows and Hyperdrive pricing were not pulled; they are not needed for this use case.
- Current exact daily send quotas for Email Service were not published on the limits page.

## Key Question 5: Cloudflare Access (Zero Trust) free tier for the internal admin dashboard

### Takeaway
Cloudflare Zero Trust (which includes Access) is free for up to 50 users, so a solo developer (plus any contractors or client logins) can put the admin dashboard and all prospect preview URLs behind SSO/email-OTP at no cost; paid seats are $7/user/month beyond that (secondary sources).

### Cited Findings
- Zero Trust free plan covers up to 50 users; paid seats are "$7/user/month" when paid annually — [Cloudflare Zero Trust pricing: is it worth it? (ControlD)](https://controld.com/blog/cloudflare-zero-trust-pricing/) (secondary) and [Cloudflare Access product page](https://www.cloudflare.com/en-au/products/cloudflare-access) (secondary: search snippet; page itself blocked in this session)
- Access policies can protect Workers routes and `workers.dev`/preview hostnames because they attach to hostnames in your zone (preview URL docs reference Access protection) — [Workers preview URLs](https://developers.cloudflare.com/workers/versions-and-deployments/preview-urls/) (secondary; see Gap)

### Inferences
- Protect `admin.yourbrand.com` (the dashboard Worker) and `*.preview.yourbrand.com` with Access; use the One-time PIN login method so prospects can view a demo with just their email if you want gated previews without Google/GitHub accounts.
- The dashboard should still validate the `Cf-Access-Jwt-Assertion` header against your team's public keys inside the Worker, so a misconfigured route cannot expose it.

### Gaps
- The official Zero Trust plans page (`www.cloudflare.com/plans/zero-trust-services/`) was blocked; the 50-user/$7 figures come from secondary sources and should be re-checked before quoting to a client.

## Key Question 6: Handoff reality — can Workers, D1, zones or registered domains move between accounts? Practical handoff procedure and three handoff models

### Takeaway
Nothing in a Cloudflare account moves to another account as an object: Workers and D1 must be redeployed/exported-imported, zones are re-added and DNS re-created, certificates are reissued, and Cloudflare-Registrar domains need a manual support request — so "transfer" is really "redeploy into the client's account", which is cheap for an Astro+wrangler project if you planned for it (one D1 per client, no Registrar in your account, secrets in a vault).

### Cited Findings
- Moving a domain between accounts means adding the domain as a new site in the target account and changing nameservers; "SSL/TLS certificates associated with your previous Cloudflare account will not be transferred to your new account"; DNS records must be exported/imported and account settings reconfigured; DNSSEC must be removed first; "If your domain is registered with Cloudflare Registrar, you need to submit a manual request to transfer the domain and its registration to a new account" — [Move a domain between Cloudflare accounts](https://developers.cloudflare.com/fundamentals/manage-domains/move-domain/)
- D1 databases are account resources; moving data is export (`POST .../d1/database/{id}/export`, during which "your D1 will be unavailable to serve queries") then import with `wrangler d1 execute --file` (5 GiB per file) — [D1 export API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/) and [D1 import/export](https://developers.cloudflare.com/d1/best-practices/import-export-data/) (secondary: search snippets)
- Account membership: "Customers on all plans can share account access with other members, but the roles available to your account depend on your plan"; Free/Pro/Business accounts have exactly two roles, "Super Administrator - All Privileges (only one allowed)" and "Administrator (unlimited)"; Administrator "can access the full account and configure dashboard, but cannot manage billing or account membership"; invite via Manage Account > Members as Super Administrator — [Manage account members](https://developers.cloudflare.com/fundamentals/manage-members/manage/) and [Roles](https://developers.cloudflare.com/fundamentals/setup/manage-members/roles) (secondary: search snippets)
- Cloudflare Registrar sells at cost (e.g. `.com` quoted at $9.77/yr by one source, ~$9.15/yr by another, with "zero markup" over Verisign's wholesale) and domains can be moved away "at any time without penalty"; transfer-out is unlock + EPP/auth code via dashboard or API — [Cloudflare becomes a registrar (BleepingComputer)](https://www.bleepingcomputer.com/news/technology/cloudflare-becomes-a-registrar-sells-domains-at-cost/) (secondary), [Bulk transfer out via API (centminmod)](https://blog.centminmod.com/2021/02/28/2310/how-to-bulk-domain-transfer-out-from-cloudflare-registrar-via-cloudflare-api/) (secondary), [Registrar domain transfers](https://developers.cloudflare.com/registrar/domain-transfers) (not fetched)
- API tokens can be scoped to a single account with permissions such as Account > Workers Scripts (Write), Workers KV Storage (Write), Workers R2 Storage (Write), D1 (Write), SSL and Certificates (Write), Account Settings (Read) — [API token permissions reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/)
- Astro env-specific builds/deploys: `CLOUDFLARE_ENV=some-env astro build && wrangler deploy` — [Astro Cloudflare adapter docs](https://docs.astro.build/en/guides/integrations-guide/cloudflare/)

### Inferences
- Handoff Model 1 — Managed on your account, client's domain via Cloudflare for SaaS custom hostname (or client zone added to your account). Effort: ~15 minutes per client (create hostname, send CNAME instructions, poll SSL status). Support burden: you own uptime, content edits, Stripe, email deliverability, and the client never touches Cloudflare. Cost to you: $0 per site up to 100 hostnames, $0.10/mo after. Best for the monthly-managed tier; the client's only asset is the domain, which should be registered in the client's name (their registrar account, or a Cloudflare Registrar account they own) so a future exit is just "change the CNAME".
- Handoff Model 2 — Deployed into the client's own Cloudflare account with you as a member. Procedure: client creates a free Cloudflare account and adds their domain (nameserver change at registrar); client invites your email as Administrator (the only non-super role on Free); you create an account-scoped API token in their account (Workers Scripts, KV, D1, R2, SSL, Workers Routes, DNS Write), add a `[env.client]`/`CLOUDFLARE_ENV` config pointing at their account ID and bindings, run `wrangler d1 create`, `wrangler d1 execute --file=export.sql`, `wrangler secret put` for Stripe/better-auth secrets, `wrangler deploy`, and attach a Workers Custom Domain; if any site feature needs Workers Paid (CPU > 10 ms, > 100k req/day, Email Service sending, D1 > 500 MB) the client must add a card and subscribe to Workers Paid ($5/mo) themselves. Effort: 1-2 hours per client the first time, ~30 minutes once scripted. Support burden: shared; you can still deploy fixes via your token, but billing, 2FA, and account recovery are theirs. Note the Free-plan role limitation: an Administrator can do almost everything except billing/membership, so the client is trusting you with their whole account, and vice versa you depend on them not revoking access mid-deploy.
- Handoff Model 3 — Full handoff: transfer the Git repository (GitHub transfer or add them as owner), deliver the D1 export, secrets list, and a runbook; the client's account becomes the sole home (if you provisioned a dedicated per-client Cloudflare account under an email alias they control, you simply make them Super Administrator by changing the login email, since only one Super Admin exists per account); you remove your membership and revoke tokens. Effort: 2-4 hours; support burden: zero ongoing (sell a paid "support retainer" if wanted). Registrar: if the domain was bought through your Cloudflare account, this model forces a manual Cloudflare support request to move the registration — avoid by buying domains in the client's own account from day one.
- Practical rule that makes all three models cheap: treat the Astro repo + wrangler config as the portable unit, keep every tenant's state in its own D1/KV/R2 namespace, and keep nothing tenant-specific in your platform account that is not reproducible from the repo and an export.

### Gaps
- No Cloudflare doc was found describing any object-level transfer of Workers, KV, R2 or D1 between accounts; the absence of such a feature is inferred from the move-domain page and the export/import docs, not from an explicit "cannot be transferred" statement.
- Whether a Cloudflare Registrar account-to-account move is reliably granted and how long it takes was not documented beyond "submit a manual request".

## Key Question 7: Account-level limits that bite at 50 to 500 client sites

On Workers Paid the ceilings that matter are 500 Workers per account, 100 Workers Custom Domains per zone, 1,000 routes per zone, 250 cron triggers per account, 128 variables per Worker, and 100 free SaaS hostnames; Workers for Platforms removes the script cap and (with a `*/*` wildcard route) the per-zone domain cap, and zones-per-account has no published limit.

### Cited Findings
- "Workers per account | 100 | 500" with footnote "If you need a higher Worker limit, use Workers for Platforms"; "Routes per zone: 1,000"; "Custom domains per zone: 100"; "If you require more than 1,000 routes or 1,000 routed zones per Worker, consider using Workers for Platforms. If you require more than 100 custom domains per zone, consider using a wildcard route"; "Number of Cron Triggers per account | 5 | 250"; "Variables per Worker (secrets + text) | 64 | 128"; "Files per Worker version | 20,000 | 100,000" — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- WfP: "unlimited number of scripts"; 1,000 scripts included in the $25 fee, then $0.02/script/month — [WfP limits](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/limits/), [WfP pricing](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/pricing/)
- D1: 50,000 databases per paid account, 1 TB total — [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)
- Cloudflare for SaaS: 100 hostnames included, 50,000 max on self-serve plans — [Cloudflare for SaaS plans](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/plans/)
- Email Routing/Sending: "30" combined domains per zone — [Email Service limits](https://developers.cloudflare.com/email-service/platform/limits/)
- DNS: zones created after September 2024 are limited to 1,000 DNS records (down from 3,000) — [Cloudflare free limits (eastondev)](https://eastondev.com/blog/en/posts/dev/20260526-cloudflare-free-limits/) (secondary)
- Turnstile: 20 widgets per account on the free plan — [Turnstile plans](https://developers.cloudflare.com/turnstile/plans/) (secondary)

### Inferences
- At 50 sites (Pattern B, standard Workers): nothing bites. At 100-200: the 100 custom-domains-per-zone cap on your preview zone forces the wildcard-route router pattern; SaaS hostnames start costing $0.10/mo each beyond 100 (i.e. $10/mo at 200); crons must already be centralized. At 400-500: the 500-Worker cap (minus your platform Workers) forces WfP, which also solves routing and adds per-tenant limits. A fleet rebuild for a template change at 200 sites × ~1-2 build minutes each consumes 200-400 Workers Builds minutes per rollout (6,000/month included on paid) or a GitHub Actions matrix.
- A single Turnstile widget key can be reused across all client sites (widgets are per-hostname set, and a widget can list multiple hostnames), so the 20-widget cap is not a fleet limit if you share one widget; this is a reasonable but unverified reading.
- The 1,000 DNS records per zone matters only if you add every client as a subdomain record in one zone; a single wildcard `*.preview.yourbrand.com` record avoids it.

### Gaps
- No published maximum number of zones per account was found; community reports suggest very large numbers are possible but nothing authoritative was located in this run.
- Workers Builds concurrency/time limits for a 200-project fleet rebuild were not examined in detail.

- Assumptions for a local-business storefront: ~20,000 dynamic requests/month per site (static assets are free), ~5 ms CPU per dynamic request, ~30 MB D1 per site, ~200 MB R2 per site, ~2 transactional emails/day per site.
- 10 sites, Pattern B (standard Workers): Workers Paid $5; requests 0.2 M, CPU 1 M ms, D1 0.3 GB, R2 2 GB, hostnames 10-20 — all inside included allowances. Total ≈ $5/month (+ $25 if WfP).

Domains, if you buy them for clients, add ≈ $10/yr per site and should be passed through.

## Key Question 9: Exact REST API calls / wrangler commands the admin dashboard would use, and token scopes

### Takeaway
Everything the dashboard needs is a handful of account- or zone-scoped v4 API calls (or the wrangler equivalents run from CI): upload a script to a dispatch namespace (or `wrangler deploy`), create a D1, create a KV namespace, attach bindings in the script's multipart `metadata`, create and poll a custom hostname, and purge cache — with the important practical constraint that `astro build` cannot run inside a Worker, so the dashboard must trigger a build runner (Workers Builds, GitHub Actions, or a small VPS) rather than call the upload API itself.

### Cited Findings
- WfP script upload: `PUT /accounts/{ACCOUNT_ID}/workers/dispatch/namespaces/{NAMESPACE_NAME}/scripts/{SCRIPT_NAME}` as multipart with `metadata={"main_module": "worker.mjs", "bindings": [...], "tags": [...], "compatibility_date": "2024-01-01"};type=application/json` plus the module file as `application/javascript+module`; list: `GET .../scripts`; delete one: `DELETE .../scripts/{SCRIPT_NAME}`; delete by tag: `DELETE .../scripts?tags={TAG}:yes`; assets: `POST .../scripts/{SCRIPT_NAME}/assets-upload-session` then `POST /accounts/{ACCOUNT_ID}/workers/assets/upload?base64=true`; binding shapes: `{"type": "kv_namespace", "name": "MY_KV", "namespace_id": "..."}` and `{"type": "assets", "name": "ASSETS"}` — [WfP API examples](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/platform-examples/)
- Standard Worker upload uses the same multipart shape at `PUT /accounts/{account_id}/workers/scripts/{script_name}` with `bindings` array and optional `bindings_inherit=strict` query param to validate inherited bindings — [Workers script upload API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/methods/update/) (secondary: search snippet)
- Static asset deploy into a namespace with wrangler: `npx wrangler deploy --name <USER_WORKER_NAME> --dispatch-namespace <NAMESPACE_NAME>`; the assets completion JWT is valid for one hour; "JWTs should only reach trusted platform services, never end-users" — [Static assets in WfP](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/static-assets/)
- Custom hostname: `POST /zones/{zone_id}/custom_hostnames` with `{"hostname": "...", "ssl": {"method": "txt"|"http", "type": "dv"}}`; readiness = `result.status == "active"` and `result.ssl.status == "active"` — [Cloudflare for SaaS getting started](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/getting-started/)
- D1 export: `POST /accounts/{account_id}/d1/database/{database_id}/export` — [D1 export API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/) (secondary)
- Preview aliases: `wrangler versions upload --preview-alias <alias>` — [Workers preview URLs](https://developers.cloudflare.com/workers/versions-and-deployments/preview-urls/) (secondary)
- Token permissions (account scope): "Workers Scripts" Read/Write ("Grants write access to Cloudflare Workers scripts"), "Workers KV Storage" Read/Write, "Workers R2 Storage" Read/Write, "D1" Read/Write, "SSL and Certificates" Read/Write, "Account Settings" Read/Write — [API token permissions reference](https://developers.cloudflare.com/fundamentals/api/reference/permissions/); third-party integration guides list the same keys (`workers_scripts`, `d1`, `workers_routes`, zone `ssl_and_certificates`) — [StackOne Cloudflare token guide](https://docs.stackone.com/connectors/cloudflare/guides/link-account/api-token) and [Infisical Cloudflare connection](https://infisical.com/docs/integrations/app-connections/cloudflare.md) (secondary)
- Astro build/deploy for a given environment: `CLOUDFLARE_ENV=<env> astro build && wrangler deploy` — [Astro Cloudflare adapter docs](https://docs.astro.build/en/guides/integrations-guide/cloudflare/)

### Inferences
- Dashboard "deploy site" flow (Pattern B or C): (1) `POST /accounts/{id}/d1/database` `{"name":"site-<slug>"}` (or `wrangler d1 create site-<slug>`) and `POST /accounts/{id}/storage/kv/namespaces` `{"title":"site-<slug>-sessions"}` on first deploy, store the returned IDs on the customer record; (2) dispatch a build job (GitHub Actions `workflow_dispatch` with `slug`, `template`, `env` inputs, or a Workers Builds project per site) whose runner runs `astro build` then `wrangler deploy --name site-<slug>` (standard) or `wrangler deploy --name site-<slug> --dispatch-namespace production` (WfP) with a generated `wrangler.jsonc` containing `d1_databases: [{binding:"DB", database_id}]`, `kv_namespaces: [{binding:"SESSION", id}]`, `assets`, `nodejs_compat`; (3) runner calls back a dashboard webhook with the version ID and preview URL; (4) dashboard writes `hostname:<slug>.preview.yourbrand.com → site-<slug>` to the routing KV.
- The D1 binding shape in multipart `metadata.bindings` is `{"type": "d1", "name": "DB", "id": "<database_uuid>"}` (unverified, last known from the Workers bindings docs; confirm against the multipart metadata reference before coding).
- "Go live" flow: `POST /zones/{saas_zone_id}/custom_hostnames` for `www.<clientdomain>` (and apex if their DNS supports flattening) with `ssl.method = "http"`, show the client the CNAME instruction (`www → sites.yourbrand.com`), poll `GET /zones/{zone_id}/custom_hostnames/{id}` until `status` and `ssl.status` are `active`, then add `hostname:www.<clientdomain> → site-<slug>` to KV; the `*/*` route on `sites.yourbrand.com` (AAAA `100::`) already points at the router/dispatch Worker.
- Cache purge: `POST /zones/{zone_id}/purge_cache` with `{"purge_everything": true}` or `{"hosts": ["www.<clientdomain>"]}` (unverified, last known; needs the zone-scoped "Cache Purge: Purge" permission). For SaaS hostnames the purge is done on your SaaS zone.
- Minimum token for the deploy runner (account-scoped, single account): Workers Scripts Write, Workers KV Storage Write, D1 Write, Workers R2 Storage Write (if media), Workers Tail Read (optional). Minimum token for the dashboard's hostname/zone operations (zone-scoped to the SaaS zone): SSL and Certificates Write, Workers Routes Write, DNS Write, Cache Purge. Keep the two tokens separate and store them as Worker secrets.

### Gaps
- No distinct "Workers for Platforms"/"dispatch namespace" permission was visible in the permissions reference excerpt; dispatch-namespace calls appear to fall under Workers Scripts Write, but this was not confirmed on a WfP page.
- The exact JSON shapes for `d1` bindings in multipart metadata and for the `purge_cache` body were not fetched in this run (marked last-known above).
- Whether the WfP namespace create endpoint is `POST /accounts/{id}/workers/dispatch/namespaces` with `{"name": ...}` (as `wrangler dispatch-namespace create` implies) was not fetched.

## Key Question 10: Alternatives (Vercel, Netlify, Fly.io, Railway, Deno Deploy, AWS Amplify, Coolify/Dokploy on a VPS, Hostinger/SiteGround for WordPress) and when they beat Cloudflare

### Takeaway
For a solo developer already on Astro+Workers, no alternative is cheaper or more automatable for "hundreds of tiny sites with custom domains"; the real competitors are not hosts but platforms the client might prefer to own (WordPress on Hostinger, Shopify/Squarespace), and a VPS with Coolify/Dokploy only wins if the sites need long-running processes, Node-native libraries, or a Postgres you want to keep.

- Cloudflare's own positioning: Workers with static assets "unifies frontend and backend in one deployment" and zero egress fees — [Cloudflare Pages vs Workers in 2026 (mecanik)](https://mecanik.dev/en/posts/cloudflare-pages-vs-workers-which-to-use-in-2026/) (secondary)

### Inferences
- Vercel beats Cloudflare only if you want its Git-preview UX and are willing to pay $20/seat; per-site cost is otherwise comparable, but handing a Vercel project to a client means them paying $20/month for Pro or living with Hobby's non-commercial terms, which is a worse handoff story than a free Cloudflare account.
- Netlify is similar to Vercel for static Astro; its credit model and Netlify-specific adapters make the stack less portable than wrangler.
- Fly.io/Railway/Coolify/Dokploy beat Cloudflare when a site needs a long-lived Node process, Puppeteer/Sharp-style native modules, websockets without Durable Objects, or a real Postgres per client; the trade is you become the sysadmin (patching, backups, TLS renewals on Coolify, a $5-20/month VPS), and per-client handoff of a Docker app is harder for non-technical owners.
- AWS Amplify beats Cloudflare only for clients already standardizing on AWS; pricing is usage-based and the egress fee ($0.15/GB) is a cost Cloudflare does not have.
- Hostinger/SiteGround WordPress beats a custom Astro site when the client insists on editing content themselves in a familiar CMS, wants a plugin ecosystem (bookings, WooCommerce), or wants to fire you and hire any local WordPress freelancer; the counter-offer is a headless CMS or a simple D1-backed admin page, but some clients will still want WordPress.
- Deno Deploy is a credible edge alternative but requires swapping the adapter and loses D1/KV/R2 bindings; no reason to switch.

### Gaps
- Netlify per-site and per-domain limits under the April 2026 credit model were not found.
- SiteGround 2026 pricing was not retrieved (treat as similar intro-then-renewal pricing to Hostinger).
- Shopify/Squarespace/Wix were out of scope here but are the realistic alternative for Etsy/Amazon sellers who want a cart; this should be covered by the business-model research track.

## Key Question 11: Gotchas — Node compatibility, CPU/subrequest/bundle limits, cold starts, Stripe SDK, images, email

### Takeaway
The known sharp edges are all documented and mostly already solved in the developer's stack: `nodejs_compat` with a compatibility date ≥ 2024-09-23, 30 s default CPU per request (5 min max on Paid), 6 simultaneous outbound connections, 128 MB memory, Stripe via `createFetchHttpClient()` and `constructEventAsync()`, no SMTP (use Cloudflare Email Service or an HTTPS email API), and image transformations that are free only up to 5,000 unique variants per month.

### Cited Findings
- Astro adapter requires `"compatibility_flags": ["nodejs_compat"]` and `"compatibility_date": "2024-09-23"` or later for Node polyfills; prerendered pages run in `workerd` by default; `Astro.locals.runtime` was removed in Astro 6 in favor of `import { env } from 'cloudflare:workers'` — [Astro Cloudflare adapter docs](https://docs.astro.build/en/guides/integrations-guide/cloudflare/)
- Limits (Free | Paid): "CPU time per HTTP request | 10 ms | 5 min (default: 30 seconds)"; "Memory per isolate | 128 MB"; "Subrequests per invocation | 50 | 10,000 (up to 10M)"; "Simultaneous outgoing connections/request | 6 | 6"; "Worker size (uncompressed) | 64 MiB"; "Variable size | 5 KB"; "Individual file size | 25 MiB" for static assets — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- WfP user Workers: CPU max 30 s per invocation (15 min for Cron/Queue consumers), "No charge or limit for duration"; default cache disabled for namespaced scripts; no `request.cf` in untrusted mode; no gradual deployments for user Workers — [WfP pricing](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/pricing/) and [WfP limits](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/limits/)
- Stripe: initialize with `Stripe(env.STRIPE_KEY, { httpClient: Stripe.createFetchHttpClient() })`; verify webhooks with `stripe.webhooks.constructEventAsync(body, signature, secret, undefined, Stripe.createSubtleCryptoProvider())` — [Announcing Stripe support in Workers (Cloudflare blog)](https://blog.cloudflare.com/announcing-stripe-support-in-workers) (secondary: search snippet)
- Email: MailChannels' free Workers API ended (June 30 / Aug 31, 2024); Cloudflare Email Service sending is Workers Paid only, 3,000/month included then $0.35/1,000, free to verified destinations; `send_email` binding can be restricted with `destination_address`/`allowed_destination_addresses`; Cloudflare docs now point to "Send Emails With Resend" as an alternative — [MailChannels EOL](https://support.mailchannels.com/hc/en-us/articles/26814255454093-End-of-Life-Notice-Cloudflare-Workers), [Email Service pricing](https://developers.cloudflare.com/email-service/platform/pricing/), [Send bindings](https://developers.cloudflare.com/email-service/configuration/send-bindings/) (secondary)
- Images: 5,000 unique transformations free, $0.50/1,000 after; adapter default `imageService: 'cloudflare-binding'` with optional build-time optimization in adapter 14.2 — [Images pricing](https://developers.cloudflare.com/images/pricing/) (secondary), [@astrojs/cloudflare 14.2.0](https://newreleases.io/project/github/withastro/astro/release/@astrojs%2Fcloudflare@14.2.0) (secondary)
- D1 per-invocation: "Queries per Worker invocation: 1,000 (Workers Paid) / 50 (Free)", "Maximum bound parameters per query: 100", "Maximum SQL statement length: 100 KB" — [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)

### Inferences
- The 6-simultaneous-connections limit matters for pages that fan out to many images/APIs (e.g. pulling an Etsy/Amazon feed); batch and cache feed data in KV/R2 with a cron rather than fetching per request.
- The 100-bound-parameters cap means bulk inserts (e.g. importing a 500-item catalog) must be chunked or use `batch()`.
- Workers have no meaningful cold start for a typical Astro SSR bundle, but a 200-site fleet on WfP shares the account's CPU allowance (60 M ms), so one runaway tenant can create overage; `limits: { cpuMs }` on `dispatcher.get()` is the fix and is a reason to prefer WfP once sites run client-supplied code or heavy SSR.
- Per-site secrets are capped at 128 variables; keep Stripe/auth secrets per site small and consider a platform-level secret store (one Worker holding secrets, service-bound) if the count grows.
- Email deliverability is the most likely support-ticket generator; verify each client's inbox as a destination (free sends) for contact-form notifications, and onboard a sending domain only for sites that email customers (order confirmations).

### Gaps
- Real-world community gotcha threads for multi-tenant WfP (Hacker News / Cloudflare community) were not surfaced by search in this session; findings above are from docs rather than practitioner reports.
- Whether `better-auth` has any Workers-specific issues in 2026 was not researched (the developer already runs it in production).

## Overall recommendation (synthesis for the report writer)

### Takeaway
Yes, Cloudflare is the right platform: the developer's current Astro-on-Workers stack is Cloudflare's recommended path, the per-site infrastructure cost rounds to zero, Cloudflare for SaaS solves "go live on the client's domain without moving accounts", D1-per-tenant makes handoff a repeatable export+redeploy, and Workers for Platforms is a $25/month upgrade path (not a prerequisite) when the fleet passes ~100-400 sites or needs per-tenant limits.

### Inferences
- Recommended architecture ("Pattern B now, Pattern C later"):
  1. Platform zone `yourbrand.com` on Workers Paid ($5/mo). Dashboard Worker at `admin.yourbrand.com` behind Cloudflare Access (free). Platform D1 holds customers, sites, deployments, hostnames, Stripe state.
  2. One Astro template repo with per-site config; each client site deploys as its own Worker `site-<slug>` with its own D1 (`site-<slug>`), its own KV session namespace, shared R2 bucket with per-site prefixes (or per-site bucket), `nodejs_compat`, static assets. Builds run in Workers Builds or GitHub Actions triggered by the dashboard; the dashboard records the version ID and `workers.dev` URL.
  3. Demo URLs: wildcard route `*.preview.yourbrand.com/*` → a small router Worker that maps `<slug>` → service binding or, after migrating to WfP, `env.DISPATCHER.get("site-<slug>")`. Gate with Access OTP if desired.
  4. Go-live without account moves: Cloudflare for SaaS on `yourbrand.com` with fallback origin `sites.yourbrand.com` (AAAA `100::`, route `*/*` → router/dispatch Worker); dashboard creates `www.<client>` custom hostname (HTTP validation), polls `ssl.status`, writes the hostname → script mapping to KV. First 100 hostnames free, then $0.10/mo.
  5. Managed tier = Model 1 (stay on your account). Buy-out tier = Model 2/3 (redeploy into the client's own free account via scoped token, D1 export/import, domain always registered in the client's name).
  6. Trigger to adopt Workers for Platforms ($25/mo): >~90 preview custom domains if you did not start with the wildcard router, >~400 Workers, any client-supplied code, or a need for per-tenant CPU/subrequest caps and outbound-request policy.
- Situations where Cloudflare is the wrong choice: the client wants WordPress/Shopify-style self-editing and plugin ecosystems; the site needs native Node modules, long-running processes, or a relational DB larger than 10 GB per tenant; the client is already paying for Vercel/AWS and wants a single bill; the business wants to resell "their own Cloudflare account" turnkey (account transfer is manual and Registrar moves need support tickets); the developer needs apex-domain support for clients whose DNS host cannot flatten CNAMEs and will not move DNS (apex proxying is Enterprise-only); or email-heavy workloads (newsletters) where Email Service quotas and deliverability ramp-up are a poor fit versus a dedicated ESP.

- The exact month the fleet would outgrow the 100 included SaaS hostnames or the 500-Worker cap depends on sales velocity, which belongs to the business-model research track.
